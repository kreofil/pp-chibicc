# Стабилизация LLVM перед переносом в main

Работа собрана в [PR №5](https://github.com/kreofil/pp-chibicc/pull/5),
ветка `feature/llvm-ir-mvp`. Это завершённый экспериментальный этап LLVM,
а не заявление о полной совместимости со всеми возможностями C.

## Что входит в этап

- Прямой x86-64 и LLVM используют общий frontend C/4П. `--backend=llvm`
  вызывает внешние `opt`/`llc`; `-S -emit-llvm` выдаёт исходный IR без LLVM.
- Реализованы скаляры, `long double`, агрегаты, битовые поля, `switch`,
  `bool`/`true`/`false`, VLA и вариадические вызовы, включая агрегатный `va_arg`.
- Поддержаны обобщения и полиморфные обработчики, смешанные native/LLVM-модули,
  константные индексы закрытых типов, таблицы и ветвление для закрытых семей.
- `--closed-program` и модуль CMake объединяют IR всей пользовательской
  программы и фиксируют разрешённые закрытые таблицы до оптимизации.
- Самокомпиляция через LLVM сравнивает IR и объекты stage2/stage3 и проверяет
  полученный компилятор. Системный toolchain по-прежнему собирает stage1.
- CI включает native, LLVM 23 и LLVM-selfhost. Исследовательские цели дают
  отчёты оптимизаций и бенчмарков; производительность не является порогом CI.

Обнаруженная при стабилизации ошибка `#pragma once` исправлена: файл
распознаётся по устройству и inode, поэтому абсолютный/относительный путь,
символическая или жёсткая ссылка не приводят к повторному включению.
Исходное имя для `__FILE__`, `#line` и поиска вложенных заголовков сохраняется.

## Как обновлять существующие программы

1. Сохраните рабочую версию и выполните чистую пересборку всех своих модулей
   и библиотек. Это особенно важно при обмене структурами с битовыми полями,
   агрегатами через регистры и `va_list`: исправлены раскладка и ABI ряда
   native-случаев. Нельзя рассчитывать на совместимость старых объектов.
2. `bool`, `true`, `false` теперь ключевые слова. Переименуйте старые
   идентификаторы с такими именами. `bool` имеет тип `_Bool`; это не полный
   переход компилятора на стандарт C23.
3. Для отсутствия обычных параметров подходят `()` и `(void)`. В обычном C
   объявление `f()` сохраняет модель C11/C17 без прототипа; в определении оно
   задаёт отсутствие параметров. Правила 4П описаны в
   [руководстве компилятора](llvm-compiler-ru.md).
4. `.ppc` компилируется без `-x c`, `.pph` подключается через `#include`.
   Для CMake сохраняется `set_source_files_properties(... PROPERTIES LANGUAGE C)`.
5. Для полной закрытой матрицы учитывайте нулевую специализацию:
   обработчик `.void` либо подходящий общий обработчик. Именованный
   `default` заменяет имя `.void` своей нулевой специализации.
6. Для native, обычного LLVM и `--closed-program` используйте разные каталоги
   промежуточных файлов. В закрытом режиме `.o` содержит специальный текстовый
   IR, а в двух остальных — обычный ELF-объект.

## Границы, которые сохраняются

Платформа — Linux x86-64 / System V. Другой `target triple` не переносит
frontend на новую архитектуру. LLVM пока диагностирует TLS, атомарные
операции, inline asm, вычисляемый `goto` и агрегатные аргументы
без прототипа. Список возможностей — в [llvm-backend-ru.md](llvm-backend-ru.md).
После этого этапа добавлена [поддержка volatile](llvm-volatile-ru.md).

Некоторые редкие битовые поля и X87-агрегаты по-разному передаются GCC и
Clang; ограничения и независимые ABI-проверки описаны в
[руководстве битовых полей](llvm-bitfields-ru.md) и
[руководстве вариадических агрегатов](llvm-vararg-records-ru.md).
Native сохраняет собственные ограничения ABI/IEEE. Динамический стек VLA
освобождается при возврате из функции, а не при выходе из каждого блока.

Оптимизация таблицы требует закрытых типов всех полиморфных параметров и
проверяемой полной матрицы обработчиков. Открытые семьи сохраняют runtime-путь.
Закрытая LLVM-сборка не переписывает исходники и не закрывает открытые типы.
Отдельная утилита такого преобразования отложена.

## Проверки перед переносом

Команды чистой сборки и форма сообщения об ошибке приведены в
[инструкции тестировщику](testing-ru.md). Перед переносом проверяются:

- чистая native-сборка и `test-all`;
- `test-llvm`, `test-llvm-stage2` и закрытые наборы stage1/stage2 на LLVM 23;
- bootstrap O0/O2 и полный `test-llvm-selfhost` при O2;
- три успешных задания CI на итоговом коммите PR и отсутствие конфликта с main;
- соответствие README, ограничений и инструкций фактическим командам.

Перенос PR в `main` выполняется отдельным действием после проверки итогового
коммита. Затем можно проверять `main` по той же инструкции и собирать отчёты
дополнительных программистов через issues. Будущая практическая задача —
компилятор нестандартного языка; её описание и минимальный набор возможностей
ещё предстоит определить.
