# Массивы переменной длины и alloca

LLVM-компилятор поддерживает локальные массивы переменной длины (VLA),
включая многомерные массивы, указатели на строки таких массивов и массивы
объектов 4П. Размер задаётся целочисленным выражением во время выполнения:

```c
int rows = 3, cols = 5;
int matrix[rows][cols];
matrix[2][4] = 42;
int (*row)[cols] = matrix;
```

Размеры сохраняются при выполнении объявления. Последующее изменение `cols`
не меняет `sizeof(matrix)` или шаг указателя `row`. Поддерживаются сложение
и вычитание указателя с целым, а также разность указателей на строки,
включая отрицательный результат. Границы вычисляются однократно; порядок
вычисления разных границ не задаётся дополнительно к правилам C.

`typedef` массива переменной длины также фиксирует размер при выполнении объявления:

```c
int n = 7;
typedef int Row[n];
n = 9;
Row matrix[2];             // 2 строки по 7 int
// sizeof(Row) == 28, sizeof(matrix) == 56 на текущей платформе
```

`sizeof` вычисляет произведения в `size_t`, до умножения расширяя границы
до 64 бит. Например, `sizeof(int[n])` при `n == 1073741824` даёт 4294967296,
не выделяя четырёхгигабайтный массив. `_Alignof` использует выравнивание
элементов массива. Учитываются выравнивание типа элемента и `_Alignas`
в объявлении VLA, включая требования выше 16 байт.

## VLA в параметрах функций

Имена предыдущих параметров доступны в размерах последующих массивов:

```c
long sum_matrix(int rows, int cols, int matrix[rows][cols]);

long sum_matrix(int height, int width, int values[height][width]) {
  long result = 0;
  for (int r = 0; r < height; ++r)
    for (int c = 0; c < width; ++c) result += values[r][c];
  return result;
}
```

Имена в прототипе и определении могут различаться. Каждый список имеет
собственную область видимости; его имена не попадают в следующий прототип
или окружающий код. Выражения границ в прототипах не выполняются. Запись
`long sum_matrix(int, int, int [*][*]);` также допустима; `[*]` используется
только в прототипах, включая типы указателей на функции.

В определении нужные размеры вычисляются при входе в функцию и сохраняются
до выполнения тела. Последующее изменение `width` не меняет шаг `values + 1`
или `sizeof(*values)`. Размеры вычисляются также для параметра-указателя
`int (*values)[width]`. `sizeof(values)` у параметра-массива даёт размер
указателя, а `sizeof(*values)` — размер строки. Поддерживаются 1D/2D/3D,
функциональные указатели/callback-функции, вариадические функции и результаты
в виде структур, включая скрытый указатель результата.

Массив передаётся через указатель на данные вызывающей стороны. Память
для копии массива не выделяется. Для массива объектов 4П их признаки
сохраняются; повторная инициализация признаков при входе не выполняется.
Размеры и переданный массив должны соответствовать друг другу по правилам C.
Поддерживается внешний список вида `int values[static restrict rows][cols]`;
`static` задаёт требование к переданному массиву, а не runtime-проверку.
Обращения с `volatile` по-прежнему диагностируются LLVM-компилятором.

В обобщённых функциях размеры могут использовать и полиморфные параметры:

```c
long matrix_sum<MatrixView *view>(int rows, int values[rows][view->cols]);
```

Вычисляются выражения определения выбранного обработчика. Прототип
обобщающей функции и невыбранные обработчики их не выполняют. Это относится
и к границам с вызовами функций или другими побочными эффектами.
Полиморфные вызовы внутри границ используют runtime-путь без локальной
подстановки защищённого `switch`; закрытая сборка может заморозить их
таблицы на общих условиях.
[Пример матрицы](../examples/llvm/ppc-vla-matrix.c) выбирает обычную или
удвоенную сумму по специализации полиморфного аргумента:

```sh
bin/ppchibicc --backend=llvm -O2 examples/llvm/ppc-vla-matrix.c -o build/ppc-vla-matrix
build/ppc-vla-matrix
```

Ожидается `matrix: sum=21, doubled=42`. Тот же исходник можно собрать
через `--closed-program -O2 --closed-family=matrix_sum`.

## Массивы объектов 4П

В [примере](../examples/llvm/ppc-vla-array.c) обобщение `Sample` закрыто,
а число элементов массива определяется параметром обычной функции:

```c
typedef struct Sample { int value; } enum { marked } const Sample;

int weight<Sample *p>() { return p->value; }
int weight<Sample.marked *p>() { return 2 * p->value; }
```

При объявлении `Sample values[n]` компилятор устанавливает нулевой признак
каждого элемента. Для `Sample.marked values[n]` устанавливается признак
`marked`. Это работает и для открытых обобщений: их значения признаков
берутся из runtime-метаданных. Поддерживаются все четыре формы обобщений,
вложенные поля и фиксированные массивы специализаций внутри элемента VLA.
Остальные поля без явной записи остаются неинициализированными по правилам C.

```sh
bin/ppchibicc --backend=llvm -O2 examples/llvm/ppc-vla-array.c -o build/ppc-vla-array
build/ppc-vla-array
```

Ожидается `VLA: sum=21`. Для исследования исходного IR:

```sh
bin/ppchibicc -S -emit-llvm examples/llvm/ppc-vla-array.c -o build/ppc-vla-array.ll
opt -S -passes='default<O2>' -verify-each build/ppc-vla-array.ll -o build/ppc-vla-array.O2.ll
```

VLA передаётся в обычную функцию или среди `...` как указатель на первый
элемент. Проверяются все режимы диспетчеризации `runtime`/`table`/`switch`
и закрытая LLVM-сборка. Наличие VLA не меняет условия закрытия таблиц:
открытые типы полиморфных параметров сохраняют runtime-диспетчеризацию.

## Представление и время жизни

Для локального массива frontend сохраняет указатель на VLA в отдельной переменной и
формирует вызов встроенного `alloca` с вычисленным числом байтов.
LLVM-компилятор преобразует его непосредственно в `alloca i8, i64 size`;
внешняя библиотечная функция не вызывается. Указатель на всю VLA и указатель
на её первый элемент адресуют выделенные данные.

Прямой вызов `alloca(size)` также поддерживается. Его параметр имеет тип
`unsigned long` (`size_t` текущей x86-64 платформы), результат выровнен как
минимум на 16 байт. Для автоматического выделения VLA применяется также
требуемое выравнивание элемента и объявления. Native-компилятор использует
тот же размер и выравнивание, сохраняя временные значения вложенных выражений.
Самостоятельный `alloca` возвращает неинициализированную память; признаки
объектов 4П в такой памяти устанавливаются явно через `init_spec`.

Как и существующая native-реализация, текущий LLVM-компилятор освобождает
динамический стек при возврате из функции. Восстановление стека при выходе
из блока VLA пока не генерируется: повторные объявления в цикле могут
увеличивать расход стека до возврата. `alloca` сохраняет память до возврата
и при вызове внутри цикла. Число элементов VLA должно быть положительным,
а требуемый объём — помещаться в доступный стек.

Агрегаты среди `...` и агрегатные `va_arg` остаются отдельным неподдержанным
случаем; передача указателя на VLA к нему не относится.

## Проверки

```sh
cmake --build build --target test-all test-llvm test-llvm-stage2
cmake --build build --target test-llvm-closed-compiler test-llvm-closed-compiler-stage2
```

Тесты проверяют адресацию и размеры 1D/2D/3D, сохранение границ в `typedef`,
побочные эффекты, размеры выше 32 бит без выделения памяти, выравнивание,
рекурсию и вложенные вызовы с аргументами на стеке. Сохранность нескольких
`alloca` проверяется после последующих выделений и вызовов. Отдельно
проверяются признаки всех форм 4П и передача VLA вариадическому мультиметоду.
Недопустимые присваивание целому VLA и инициализатор VLA диагностируются.
Сравниваются native, LLVM O0/O2 и закрытая сборка, включая stage2;
обычный C-тест также проверяется GCC/Clang.

`test/vla-params.c` проверяет прототипы, переименование и вложенные области
видимости параметров, сохранённые размеры, побочные эффекты, указатели на
строки, callback-функции, `stdarg` и агрегатные аргументы/результаты. Отдельный
host-модуль вызывает сгенерированную функцию и вызывается ею. Границы
неиспользованных прототипов не добавляют runtime-зависимости закрытой сборке.
`test/ppc-vla-params.c` проверяет выбранные обработчики, мультиметоды,
открытые типы, признаки переданного массива и полиморфный вызов в границе.
Сценарий `cmake/run-vla-parameter-tests.sh` проверяет все режимы диспетчеризации
и 15 ошибочных объявлений с точной диагностикой в обоих бэкендах.
