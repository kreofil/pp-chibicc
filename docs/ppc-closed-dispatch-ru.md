# Локальная оптимизация вызовов закрытого обобщения

После введения [константных индексов](ppc-closed-indices-ru.md) ppchibicc
поддерживает локальную оптимизацию диспетчеризации для функции с одним
процедурным аргументом закрытого типа `case`, `enum`, `nullptr` или `union`.
Общий frontend формирует обычный AST, доступный обоим бэкендам.

## Когда применяется оптимизация

В текущей единице трансляции должны быть явно объявлены конкретные обработчики
для всех индексов закрытой семьи, включая нулевой. Их тела могут находиться
в другом файле: для построения массива адресов достаточно объявлений.
Обработчики могут появляться после вызывающей функции — решение принимается
после разбора всей единицы трансляции.

Для ограничения роста кода первая реализация обрабатывает не более 16
альтернатив, включая нулевую. Неполный локальный набор, открытый/непрозрачный
тип и функции с несколькими процедурными аргументами сохраняют runtime-путь.
Общий обработчик не считается доказательством, что известны все конкретные
обработчики. Проверки полноты абстрактных закрытых функций сохраняются.

Для каждого подходящего набора создаётся частный неизменяемый массив известных
адресов. В LLVM это `internal constant [N x ptr]`; в native — данные в секции
`.data.rel.ro`. Существующая общая runtime-таблица и её регистрация сохраняются
для совместимости с другими единицами трансляции и native/LLVM-объектами.
Это пока не замена всей регистрации на этапе компоновки.

## Почему остаётся проверка адреса

`const` закрывает набор специализаций типа. Другой модуль по-прежнему может
зарегистрировать обработчик существующей специализации, в том числе со
статическим связыванием. Поэтому известный локально адрес нельзя безусловно
подставлять вместо фактически зарегистрированного.

Компилятор один раз получает признак объекта и адрес активного обработчика.
Затем сравнивает его с адресом из частного массива:

```text
active = runtime_table[tag]
if active == known_handlers[tag]:
    вызов известного обработчика
else:
    вызов active
```

В `switch`-представлении известный путь разбивается по `tag` на прямые вызовы.
LLVM может встроить их тела. Запасной косвенный путь выполняет фактически
зарегистрированный обработчик, если его адрес отличается. Перед разветвлением сохраняются значения
аргументов, включая копии структур. Вложенные вызовы вычисляются один раз;
массивы и имена функций преобразуются в указатели. Для порядка вычисления
обычных аргументов действуют правила C. Следующий вызов учитывает изменение
признака объекта, в том числе сделанное предыдущим обработчиком.

Полностью исключить запасной путь и runtime-регистрацию можно будет на этапе,
где доказана полнота всех участвующих модулей и отсутствие других регистраций.
Одной закрытости типов для такого вывода недостаточно.

## Выбор представления

```sh
bin/ppchibicc --backend=llvm --ppc-dispatch=switch -O2 program.c -o program
```

| Режим | Поведение |
| --- | --- |
| `auto` | Значение по умолчанию: `switch` для LLVM, `runtime` для native |
| `runtime` | Существующий вызов через общую runtime-таблицу |
| `table` | Неизменяемый массив известных адресов, проверка активного адреса и запасной вызов |
| `switch` | Тот же массив и проверка, затем `switch` с прямыми вызовами; запасной runtime-вызов сохраняется |

Режимы действуют при разборе C/4П-исходников. Уже сформированные `.ll`/`.bc`
сохраняют своё представление. Явные `table`/`switch` доступны также native;
для неподходящих функций любой режим оставляет runtime-диспетчеризацию.
Опция передаётся дочернему компилятору и работает при раздельной сборке.

В проверенном примере `closed_area` после `default<O2>` LLVM 19/21/23 встраивает
известные обработчики из прямых ветвей `switch`. Один косвенный вызов остаётся
для несовпадения адреса. Проверка варианта `table` показывает, что LLVM может
объединить вызовы в косвенный вызов через выбранный указатель: неизменяемость
локального массива сама по себе не гарантирует девиртуализацию с такой
проверкой. Поэтому для LLVM в `auto` выбран `switch`.

Дополнительные проверки и прямые ветви увеличивают код. Изменение статических
счётчиков не является измерением ускорения; выигрыш зависит от обработчиков,
распределения специализаций и частоты запасного пути.

## Проверка и примеры

```sh
cmake -S . -B build -DPPCHIBICC_LLVM_VERSION=23
cmake --build build --target test-all test-llvm test-llvm-stage2

bin/ppchibicc --backend=llvm -O2 test/ppc-closed-dispatch.c \
  -o build/ppc-closed-dispatch
build/ppc-closed-dispatch
```

Ожидается `closed dispatch OK`. Для сравнения добавьте
`--ppc-dispatch=runtime`, `--ppc-dispatch=table` или `--ppc-dispatch=switch`.

В `test-llvm` и `test-llvm-stage2` включён сценарий
`cmake/run-llvm-closed-dispatch-tests.sh`. Он проверяет все режимы на native
и LLVM O0/O2, правильность IR и неизменяемых массивов, поздние определения,
все четыре вида типов, `void`, вещественные и структурные результаты,
скрытый `sret`, вариадические обработчики (включая строки/указатели на
функции), вложенные вызовы, изменение признака и побочные эффекты аргументов. Дополнительный модуль регистрирует свой обработчик с
другим результатом. Прямой и обратный порядок объектов проверяют оба пути,
в том числе в смешанных native/LLVM-сборках.

Исследование [llvm-dispatch-demo](llvm-dispatch-ru.md) использует `auto`.
Для повторения с другой стратегией:

```sh
PPCHIBICC_PPC_DISPATCH=runtime cmake --build build --target llvm-dispatch-demo
PPCHIBICC_PPC_DISPATCH=table cmake --build build --target llvm-dispatch-demo
PPCHIBICC_PPC_DISPATCH=switch cmake --build build --target llvm-dispatch-demo
```

Каждый запуск обновляет `build/llvm-dispatch-demo`; выбранная стратегия
записывается в отчёт и manifest. Исходный IR и тела функций позволяют
отдельно изучать известный и запасной пути.

Дальнейшая оптимизация мультиметодов ограничена случаями, когда **закрыты все
процедурные аргументы**. Сбор окончательного набора обработчиков из нескольких
модулей и возможный отказ от запасного пути — отдельный следующий этап.
