# Константные индексы закрытых обобщений

Для обобщений `case`, `enum`, `nullptr` и `union`, определённых с завершающим
`const`, ppchibicc фиксирует индексы специализаций при компиляции:

- само обобщение и его нулевая специализация имеют индекс `0`;
- именованный `default` в `case` тоже занимает `0` и заменяет имя `.void`;
- остальные специализации получают `1, 2, …` в порядке описания;
- `get_spec_size(Type)` возвращает число всех альтернатив, включая нулевую.

Для закрытого типа `get_subtype_index(Type.specialization)` и
`get_spec_size(Type)` являются целочисленными константными выражениями.
Они подходят для меток `case`, C-перечислений, границ глобальных массивов и
статических инициализаторов. Доступны как имена `typedef`, так и запись
`struct Type.specialization`.

Это общий механизм frontend для native- и LLVM-бэкендов. Автоматические
`#define` и дополнительные имена констант не создаются. Операции разбираются
после препроцессора, поэтому их нельзя использовать для вычислений `#if`.

## Пример `switch`

```c
typedef struct Figure { int color; } case {
  struct { int width, height; } rect;
  struct { int a, b, c; } trian;
} const Figure;

enum { figure_count = get_spec_size(Figure) }; // 3
int counters[get_spec_size(Figure)];

int classify(Figure *p) {
  switch (get_spec_var_index(p)) {
    case get_subtype_index(Figure):       return 0;
    case get_subtype_index(Figure.rect):  return 1;
    case get_subtype_index(Figure.trian): return 2;
    default:                             return -1;
  }
}
```

Числа в `case` можно получать напрямую через `get_subtype_index`.
`get_spec_var_index` читает фактический признак объекта; его аргумент
вычисляется один раз. Закрытость типа не запрещает изменение специализации
объекта через поддерживаемые операции, например присваивание признака `enum`
или `init_spec`.

## Инициализация и раздельная компиляция

Константные номера используются при локальной и глобальной инициализации,
вложенных объектах и массивах, присваивании признаков `enum`, `create_spec`,
`init_spec`, `get_spec_ptr` и регистрации обработчиков.

Глобальные объекты с явным инициализатором содержат закрытые признаки
непосредственно в данных объектного файла. Для объектов без явного
инициализатора сохраняется прежняя инициализация при запуске: это позволяет
сохранить объединение tentative/common-определений C из разных единиц
трансляции. Вложенные открытые обобщения также сохраняют runtime-инициализацию.

Служебные общие переменные индексов и количества остаются доступны модулям,
которые видят только непрозрачное предварительное объявление типа. Их
конструкторы записывают фиксированные номера и количество для закрытой
семьи; порядок подключения объектных файлов не задаёт нумерацию.
В таком непрозрачном модуле `get_spec_size` остаётся runtime-выражением,
поскольку закрытое определение ему неизвестно.

Числовое кодирование признаков закрытых типов изменилось по сравнению с
прежним назначением номеров при запуске. **После обновления нужна чистая
пересборка всех объектов и библиотек, использующих эти типы**, включая
смешанные native/LLVM-модули. Изменение порядка специализаций в закрытом
определении также меняет их номера и требует согласованной пересборки.

У открытых обобщений ненулевые индексы по-прежнему назначаются при запуске;
их порядок не гарантируется. `get_subtype_index(Open.specialization)` и
`get_spec_size(Open)` не становятся константами для `case`/C-перечислений.
Нулевая специализация любого обобщения сохраняет индекс `0`.

## Граница первого этапа

На этом этапе изменены константные индексы и размеры. Вызовы обобщающих
функций продолжают использовать runtime-таблицы с регистрацией обработчиков.
Сохраняются общий обработчик, конкретная нулевая специализация и проверки
полноты закрытых обобщений.

[Следующий этап уже реализован локально](ppc-closed-dispatch-ru.md):
неизменяемый массив известных адресов и прямые ветви `switch` для функции
с полным локальным набором обработчиков. Общий обработчик заполняет свободные
ячейки, конкретные имеют приоритет; размер всей матрицы ограничен 16 ячейками.
Проверка активного адреса сохраняет совместимость с внешней регистрацией.
Для мультиметода такая оптимизация применяется **только когда все
процедурные аргументы имеют закрытые типы**. При наличии хотя бы одного
открытого или непрозрачного типа сохраняется текущая runtime-диспетчеризация.
Преобразование открытой программы в закрытую отдельной утилитой в этот этап
не входит.

## Проверка

```sh
cmake -S . -B build -DPPCHIBICC_LLVM_VERSION=23
cmake --build build --clean-first --target test-all test-llvm test-llvm-stage2

bin/ppchibicc --backend=llvm -O2 test/ppc-closed-indices.c \
  -o build/ppc-closed-indices
build/ppc-closed-indices
```

Ожидается `closed indices OK`. Этот исходник подходит и для native-бэкенда.
Общие native/stage2 и LLVM O0/O2-проверки покрывают все четыре формы, пустые
и именованные нулевые альтернативы, `switch`/enum/глобальные константы,
инициализацию, изменение признаков и побочные эффекты. Независимый модуль
GCC/Clang проверяет готовность явно инициализированных закрытых данных до
фазы инициализации глобальных объектов. Межмодульные проверки включают
обработчики из разных файлов, непрозрачное объявление и смешанные
native/LLVM-объекты.
