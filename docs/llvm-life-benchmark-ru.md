# Вычислительное ядро «Жизни» через x86-64 и LLVM

Цель `llvm-life-bench` сравнивает прямой x86-64 backend, отдельную оптимизацию
LLVM-модулей при O2 и общую LLVM O2-сборку через `--closed-program`.
Используются исходные `map.c`, `eworld.c` и их заголовки из
`examples/games/conway-life/tor/conway-life-poly-tor/src`.
Функции вычисления соседей, нового поколения и обмена карт не меняются.

Открытое обобщение `Cell` сохраняется. Матрицы `DrawCell`, `isLife`,
`CreateCell`, `NewCellState` должны оставаться `excluded`; отсутствие выбранных
статических таблиц и удалённых runtime-функций проверяется автоматически.
Здесь измеряется общая оптимизация IR, а не эффект закрытия исходных типов.

## Запуск

Нужны Python 3.8+, GNU `size`, системный C toolchain и LLVM-инструменты
`llvm-as`, `opt`, `llc`, `llvm-link` одной major-версии, не ниже 19.

```sh
cmake -S . -B build -DPPCHIBICC_LLVM_VERSION=23
cmake --build build --target test-llvm-life-bench
cmake --build build --target llvm-life-bench
cat build/llvm-life-bench/report.md
```

`test-llvm-life-bench` выполняет только проверки корректности, без калибровки
и выборок времени. `test-llvm-life-bench-stage2` повторяет их компилятором
stage2. Оба target входят в LLVM CI без порогов быстродействия.

Полный запуск использует общую методику `cmake/llvm_bench.py`: по умолчанию
семь повторов, калибровка на 0,1 секунды, привязка к одному доступному CPU,
случайный порядок вариантов. Число раундов внутри одной нагрузки одинаково
для всех трёх программ и выбирается по самому быстрому варианту.

Настройки задаются окружением:

```sh
PPCHIBICC_BENCH_SAMPLES=7 PPCHIBICC_BENCH_SECONDS=0.1 \
  cmake --build build --target llvm-life-bench
```

Поддерживаются также `PPCHIBICC_BENCH_SEED` и `PPCHIBICC_BENCH_CPU` с теми же
правилами, что у остальных LLVM-бенчмарков. Каждый запуск получает новый
каталог `run-*`; верхний `report.md` относится к последнему успешному запуску.

## Нагрузки и границы измерения

Четыре нагрузки: исходный блинкер и глайдер на торе 16×16 и псевдослучайные
карты 32×32 и 64×64. Seed задаётся при запуске программы; генератор LCG и
снимки начальных карт фиксируются в артефактах.

Каждый измеряемый раунд:

1. Восстанавливает обе рабочие карты из исходного состояния.
2. Меняет одну клетку в зависимости от номера фазы (0..7).
3. Выполняет 32 поколения исходными `LifeNextState` и `MapExchange`.
4. Вычисляет контрольную сумму всей итоговой карты и число живых клеток.

Фазы циклически меняются, поэтому повторяемые раунды не имеют одного и того
же результата. В LLVM IR функция `life_run` помечается `noinline`; наличие
этой границы и вызовов из прогрева/измеряемого цикла проверяется после O2.
Исходный x86-64 backend не выполняет встраивание. Внутренние функции ядра
доступны обычной оптимизации LLVM.

За границами измерения остаются запуск процесса, конструкторы, выделение
контекста, создание исходной карты, восемь прогревочных раундов и печать.
В измерение входят восстановление карт и проверка итогового состояния.
Показатель нс/обновление клетки нормирует время всего раунда на число
поколений × ширину × высоту; он не измеряет отдельно одну операцию поля.

Таймер также обрабатывается соответствующим pipeline. Это сравнение полных
вариантов программы, не изоляция стоимости одной косвенной диспетчеризации.
Интерактивный `main`, загрузка файла, анимация и `usleep` заменены отдельным
конечным тестовым запуском, не входящим в исходный проект игры.

## Независимая проверка

Python-модель считает восемь соседей, исключая центр; исходная программа
считает девять клеток и вычитает живой центр. Для всех восьми фаз независимо
вычисляются итоговые карты, FNV-64, число живых клеток и суммы результатов
повторяемых раундов. Проверяется также исходный fingerprint и прогрев.
Внутри C-стенда число клеток в состоянии `EWorld` сравнивается с фактической
популяцией, а счётчик поколений — с запрошенным числом.

Проверки охватывают четыре рабочих размера и торы 1×1 и 3×5, ноль поколений,
1/7/32 поколения, граничные seeds и 1/9 раундов (включая переход через все
фазы). Это 144 успешных запуска на каждый компилятор и 45 проверок неверных
аргументов. Каждый калибровочный и измеряемый запуск тоже сверяется с моделью.

## Исправления, найденные на этой нагрузке

Прежний x86-64 backend разворачивал присваивание структуры в пару команд
для каждого байта. Три копирования карт в стенде создавали около 1,7 МБ
`.text`. Для структур/объединений больше 64 байт теперь используется компактное
`rep movsb`, с сохранением адреса значения и используемых регистров.
Размер `.text` того же стенда сократился с 1 702 904 до 24 926 байт.

Связанный регрессионный тест обнаружил прежнюю ошибку возврата больших
структур: `rax` содержал адрес исходника вместо адреса скрытого буфера
результата, требуемого System V ABI. Теперь возвращается адрес буфера;
копирование большого результата также использует `rep movsb`.
Для native-проектов следует пересобрать объекты, содержащие такие функции:
старые определения всё ещё содержат ошибку возврата. Объекты системных
компиляторов с корректным System V ABI этим исправлением не затрагиваются.

`test/large-copy.c` проверяет нечётный размер, невыровненные поля, защитные
байты, самоприсваивание, цепочки/значение присваивания, передачу со стековыми
аргументами, возврат по значению и union. Он запускается обычным набором
stage1/stage2 и через LLVM O0/O2; отдельно сверялся с системным GCC.

## Локальный результат

Полный запуск LLVM 23.1.6 на commit `c6b6187`, семь повторов на одном CPU,
дал 84 замера. Медианы в нс/обновление клетки (в скобках MAD):

| Нагрузка | x86-64 | LLVM O2 | Общая LLVM O2 |
| --- | ---: | ---: | ---: |
| blinker-16 | 225,46 (3,3%) | 33,38 (1,4%) | 33,30 (0,8%) |
| glider-16 | 224,91 (1,5%) | 34,23 (3,1%) | 33,67 (1,5%) |
| random-32 | 250,49 (2,2%) | 53,64 (2,2%) | 56,08 (2,1%) |
| random-64 | 248,45 (4,3%) | 61,21 (4,2%) | 58,75 (3,6%) |

Обычная и общая LLVM-сборки на этих входах близки; направление небольшой
разницы зависит от нагрузки. Устойчивый общий выигрыш от объединения IR
этим прогоном не установлен. Замеров с CPU/wall < 0,8 не было.

Размер `.text` всего стенда: native 24 926, LLVM O2 6594, общая O2 6968 байт.
Для открытых таблиц общая оптимизация не гарантирует уменьшения кода.
Сравнение времени с другими программами или машинами требует новых замеров.

## Артефакты

Сохраняются исходные файлы и их SHA256, копии скриптов, исходный и
оптимизированный IR, матрицы и closure manifests, ELF-размеры, версии
инструментов, команды, результаты проверок и начальные карты.
`build.json`, `checks.json`, `datasets.json` описывают сборку и эталоны.
Полный запуск дополнительно сохраняет `samples.json/tsv`, `summary.tsv`,
медианы wall/CPU-времени, MAD и CPU/wall. Поле `calls` в сырых данных —
число обновлений клеток, используемое общей методикой нормирования.

Результаты относятся к данной машине и входам. MAD показывает разброс,
не доверительный интервал; небольшие различия близких вариантов требуют
осторожной интерпретации. Размер исполняемого файла не доказывает ускорения.
