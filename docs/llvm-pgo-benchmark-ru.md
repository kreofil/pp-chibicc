# Измерение быстродействия диспетчеризации с PGO

Цель `llvm-pgo-bench` сравнивает исходный x86-64 backend ppchibicc, LLVM O2
и LLVM PGO + O2. Она использует ядро и обработчики из
[эксперимента с профилем](llvm-pgo-ru.md), добавляя измерение времени и
контроль результатов. Исходники компилятора и семантика 4П не меняются.

## Запуск

Нужны Linux x86-64, инструменты и compiler-rt для LLVM/Clang 23, как для
`llvm-pgo-demo`, а также Python 3.8 или новее со стандартной библиотекой.
Проверено с Clang/LLVM 23.1.6.

```sh
cmake -S . -B build-llvm23 -DPPCHIBICC_LLVM_VERSION=23
cmake --build build-llvm23 --target llvm-pgo-bench
cat build-llvm23/llvm-pgo-bench/report.md
```

Альтернатива: `make llvm-pgo-bench BUILD_DIR=build-llvm23`.
Если Python не найден автоматически, задайте
`-DPython3_EXECUTABLE=/path/to/python3` при конфигурации CMake.
Остальные цели не требуют Python.

Цель сначала заново запускает `llvm-pgo-demo` внутри
`build-llvm23/llvm-pgo-bench/demo`: собирает профиль и выполняет проверки
корректности. Время этого этапа не входит в замеры. Отсутствие зависимости
останавливает цель с диагностикой; отсутствие ускорения не считается ошибкой.

Запускайте измерения без параллельной сборки или тяжёлой работы на машине.
По умолчанию дочерние процессы закреплены за одним разрешённым CPU.
Это локальное свойство процесса измерений, системные настройки не меняются.

## Что сравнивается

| Нагрузка | Объекты в `dispatch_many` | Связь с обучением |
| --- | --- | --- |
| `rectangle` | Два указателя на прямоугольник | Тот же обработчик, что в профиле |
| `square` | Два указателя на квадрат | Только отсутствовавший в профиле обработчик |
| `mixed` | Прямоугольник и квадрат | Половина вызовов совпадает с профилем |
| `growing` | Новая специализация и прямоугольник | Половина вызовов направлена в отдельный модуль |

Профиль содержит только 4096 вызовов `rectangle`. Это намеренно узкое
обучение: контрольные нагрузки показывают зависимость от профиля и работу
общего пути. Они не являются представительным набором для любой программы.

`growing` увеличивает `visits` и своё поле на 0.5 при каждом вызове.
Прогрев тоже меняет состояние; ожидаемые сумма и счётчик это учитывают.
Каждый замер выполняется в новом процессе, начиная с одинакового состояния.
Смена специализации через `init_spec` проверяется прежним `llvm-pgo-demo`;
в измеряемые нагрузки она не включена.

Варианты LLVM используют **ровно те же `O2/core.o` и `PGO/core.o`**, которые
прошли проверки в `demo`, и один общий O2-объект расширения. Нативный вариант
использует исходные native-объекты ядра и расширения. Инструментированный
обучающий объект не участвует в измерении; compiler-rt не линкуется с
измеряемыми программами. CPU LLVM — `x86-64`, параметры `llc` одинаковы.

Обычный C-файл [timer.c](../examples/llvm/pgo-bench/timer.c) компилируется
системным компилятором с `-O2 -fno-lto` один раз и линкуется со всеми тремя
вариантами. Он взаимодействует с объектами 4П через непрозрачные указатели
и скалярные аргументы. Подготовка объектов находится в отдельном
[setup.c](../examples/llvm/pgo-bench/setup.c), собранном ppchibicc.
LTO не используется, поэтому таймер не встраивает и не удаляет исследуемый
вызов `dispatch_many`.

## Методика

1. Каждый процесс готовит два объекта и выполняет 8 прогревочных пакетов.
   Пакет — один `dispatch_many(shapes, 4096)`.
2. Измеряемый цикл повторяет этот пакет. `CLOCK_MONOTONIC` даёт прошедшее
   время, `CLOCK_PROCESS_CPUTIME_ID` — время CPU. Цикл суммирует результаты;
   после измерения проверяются сумма и число изменений `visits`.
3. Калибровка подбирает **одно число пакетов на нагрузку для всех вариантов**,
   ориентируясь на самый быстрый вариант и целевую длительность 0.1 с.
   Медленный вариант получает ту же работу и может выполняться дольше.
4. Каждый блок содержит все 12 сочетаний нагрузки и backend. Порядок
   перемешивается с фиксированным seed. По умолчанию выполняется 7 блоков.
5. Отчёт показывает медиану нс/вызов и MAD: медиану абсолютных отклонений
   от медианы. Сохраняются также min/max и время CPU для каждого замера.

Создание процесса, конструкторы 4П, подготовка объектов, прогрев и печать
результата находятся вне интервала. Накладные расходы внешнего цикла
вызовов `dispatch_many` входят в измерение одинаковым способом.

До калибровки каждый backend дополнительно проверяется на 1 и 3 пакетах:
независимый Python-цикл вычисляет ожидаемый результат по вызовам. Проверяются
и ошибки аргументов. В каждом полном замере C-таймер проверяет результат
по арифметической формуле; некорректный результат останавливает эксперимент.

Параметры задаются переменными окружения на время запуска:

```sh
PPCHIBICC_BENCH_SAMPLES=11 PPCHIBICC_BENCH_SECONDS=0.2 \
  cmake --build build-llvm23 --target llvm-pgo-bench
```

| Переменная | По умолчанию | Допустимые значения |
| --- | --- | --- |
| `PPCHIBICC_BENCH_SAMPLES` | `7` | От 3 до 101 повторов |
| `PPCHIBICC_BENCH_SECONDS` | `0.1` | От 0.01 до 1 с, цель калибровки |
| `PPCHIBICC_BENCH_CPU` | `auto` | Первый разрешённый CPU; номер CPU или `none` для отключения привязки |
| `PPCHIBICC_BENCH_SEED` | `20261111` | Целое от 0 до 2³²−1 |

`auto` выбирает CPU из текущей разрешённой affinity. Явный номер должен
принадлежать этому набору. Число пакетов ограничено 1 000 000; фактическая
длительность и объём работы записаны в сырые данные. Это ориентир для
калибровки, а не жёсткая длительность каждого замера.

## Как читать результат

`O2/PGO` — отношение медианного времени O2 к медианному времени PGO.
Значение больше 1 означает ускорение на данной нагрузке, меньше 1 — замедление.
Native служит исходной точкой сравнения; у этого backend нет оптимизирующего
pipeline, поэтому отношение native к LLVM не выделяет эффект профиля.

PGO включает весь стандартный pipeline использования профиля. Разница времени
может отражать встраивание горячего обработчика, размещение блоков и другие
преобразования; она не изолирует стоимость одной проверки адреса.

MAD характеризует разброс замеров и не является доверительным интервалом.
Отчёт отмечает ряды с MAD выше 10% и замеры с CPU/wall ниже 0.8. Привязка CPU
и перемешивание уменьшают часть шума, но не устраняют влияние частоты CPU,
соседних процессов, размещения кода и среды виртуализации.

Это микробенчмарк двух чередующихся объектов и коротких обработчиков.
Его результаты относятся к конкретной машине, сборке LLVM и данным.
Следующий эксперимент на прикладной программе должен включать её собственные
нагрузки обучения и проверки.
Такое продолжение реализовано в цели `llvm-figures-bench`:
[коллекция фигур, сортировка и состав обучения](llvm-figures-benchmark-ru.md).

## Наблюдение на LLVM 23.1.6

Прогон 2026-11-11, Linux x86-64, KVM, Intel Xeon Platinum 8573C.
Таймер собран Clang 23.1.6. Использованы 7 повторов, цель калибровки 0.1 с,
seed `20261111`, привязка к CPU 0. В таблице — медиана нс/вызов; в скобках
MAD в процентах от медианы.

| Нагрузка | native | O2 | PGO | O2/PGO |
| --- | ---: | ---: | ---: | ---: |
| rectangle | 9.941 (0.8%) | 4.664 (1.7%) | 0.633 (3.0%) | 7.371 |
| square | 11.182 (1.3%) | 4.482 (1.2%) | 2.435 (1.1%) | 1.841 |
| mixed | 10.086 (1.5%) | 4.591 (0.6%) | 1.531 (1.5%) | 2.999 |
| growing | 11.769 (2.2%) | 4.650 (2.3%) | 1.518 (0.9%) | 3.063 |

Всего получено 84 измерения. Все проверки суммы и состояния объектов пройдены;
в каждом блоке представлены все сочетания, работа на одной нагрузке одинакова.
PGO оказался быстрее и на `square`, где выполняется общий косвенный путь.
Это иллюстрирует влияние всего pipeline: в листингах различаются размещение
блоков и сохранение промежуточной суммы вокруг вызова. Поэтому эту разницу
нельзя приписывать исключительно замене косвенного вызова прямым.

## Артефакты

В `build-llvm23/llvm-pgo-bench` сохраняются:

- `report.md` — сводная таблица времени;
- `samples.json` — калибровка, проверки, настройки, affinity, контрольные
  суммы исполняемых файлов и каждый завершённый замер в порядке выполнения;
- `samples.tsv`, `summary.tsv` — сырые замеры и статистика для анализа;
- `manifest.txt` — параметры сборки таймера, версии, сведения CPU и хеши;
- `source/`, `objects/`, `bin/` — исходники таймера, общие объекты и три программы;
- `demo/` — полный воспроизводимый эксперимент PGO, его профиль, IR и manifest.

Повторный запуск создаёт свежий профиль и очищает старую сводку времени.
Итоговый `report.md` появляется только после успешных замеров. Хеши
исполняемых файлов проверяются до и после измерений.
