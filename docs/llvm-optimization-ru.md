# Первое исследование оптимизаций LLVM и 4П

Цель эксперимента — увидеть, как обычные проходы LLVM обрабатывают IR,
сгенерированный ppchibicc: локальные структуры, вычислительный цикл и вызов
обработчика 4П через runtime-таблицу. Сравнивается структура кода; время
выполнения и ускорение здесь не измеряются.

## Запуск

Из корня репозитория:

```sh
cmake -S . -B build
cmake --build build --target llvm-opt-demo
cat build/llvm-opt-demo/report.md
```

Альтернатива для корневого Makefile: `make llvm-opt-demo`.
Нужны `llvm-as`, `opt` и `llc` одной версии, LLVM 19 или новее, а также обычные
инструменты сборки Linux, включая shell и `awk`. Проверены LLVM 19.1.7 и 21.1.8.
Выбор версии и настройка путей описаны в [руководстве backend](llvm-backend-ru.md#проверки).
Цель запускается отдельно от `test-all`.

Результаты сохраняются в каталоге сборки, например `build/llvm-opt-demo`:

| Файл или каталог | Содержимое |
| --- | --- |
| `source.c`, `expected.txt` | Копии исследуемой программы и ожидаемого вывода |
| `input.ll`, `input.bc` | IR от ppchibicc и его bitcode |
| `manifest.txt` | Версии, пути, commit и состояние рабочей копии, контрольные суммы, параметры платформы |
| `pipelines.tsv` | Точные последовательности проходов и настройки генерации ассемблера |
| `metrics.tsv` | Статические счётчики для всего модуля и каждой функции |
| `report.md` | Таблицы для модуля и трёх исследуемых функций |
| `raw/`, `mem2reg/`, `sroa/`, `O2/` | Результаты каждого pipeline |

В каждом каталоге pipeline находятся `program.ll`, `program.bc`, `program.s`,
`program.o`, `program.exe`, вывод выполнения и фрагменты функций `grow.txt`,
`local_sum.txt`, `dispatch_sum.txt`. Фрагменты предназначены для чтения и
сравнения; отдельными собираемыми модулями LLVM они не являются.
`passes.txt` содержит развёрнутый список проходов, полученный через
`-print-pipeline-passes`. `properties.txt` сохраняет стандартный анализ LLVM
`print<func-properties>`, включая числа инструкций, загрузок и записей.

## Что делает программа

Исходник — [examples/llvm/optimization.c](../examples/llvm/optimization.c).
Параметр командной строки задаёт число итераций от 0 до 32; без параметра
используется 4. Публичные функции оставляют отдельные тела для изучения,
даже когда O2 встраивает их вызовы в другие функции.

- `grow` принимает и возвращает `Pair` из двух `double`, увеличивая оба поля.
- `local_sum` хранит локальную структуру, вызывает `grow` в цикле и суммирует поля.
- `dispatch_sum` чередует обобщённые указатели на прямоугольник и квадрат и
  вызывает обобщающую функцию `Area`, передавая `Pair` как обычный параметр.

При этих данных первая сумма равна `n*(n+9)/2`. Площадь прямоугольника с
прибавленными размерами равна 15, квадрата — 18; вторая сумма складывает их
по очереди. Проверяются входы 0, 1, 4, 7 и 31, запуск без аргументов и отказ
с кодом 2 для -1 и 33. Существующий backend x86-64 и все четыре LLVM-варианта
должны дать фиксированный ожидаемый результат. Например:

```sh
build/llvm-opt-demo/O2/program.exe 7
```

```text
n=7 locals=56.00 dispatch=114.00
```

## Сравниваемые преобразования

Все варианты независимо получают один и тот же `input.bc`.

| Каталог | Аргумент `opt -passes=` | Назначение |
| --- | --- | --- |
| `raw` | `verify` | Проверка и каноническая печать исходного IR |
| `mem2reg` | `function(mem2reg)` | Продвижение подходящих скалярных переменных из памяти в SSA |
| `sroa` | `function(sroa,mem2reg)` | Разбор локальных агрегатов и продвижение частей в SSA |
| `O2` | `default<O2>` | Стандартный набор оптимизаций LLVM уровня O2 |

SROA сам умеет продвигать разобранные части в SSA; `mem2reg` после него
не обязательно добавляет изменения. В этом эксперименте сочетание записано
явно. IR каждого варианта проверяется через `-verify-each` и `llvm-as`.

Для `opt` используется `-mcpu=x86-64`; генерация ассемблера во всех вариантах
одинакова: `llc -O=2 -mcpu=x86-64 -relocation-model=pic`. Текст `program.s`
сохраняется для изучения. Объектный файл `program.o` создаётся отдельным
запуском того же `llc` с `-filetype=obj` и теми же настройками; системный
C-компилятор линкует готовый объект. Это позволяет использовать новый LLVM
с системным GNU as, который ещё не понимает некоторые выводимые директивы,
например `.prefalign`. Таким образом, меняется
последовательность проходов IR при фиксированных настройках генерации
машинного кода. Даже для `raw` сам `llc` выполняет свою работу по оптимизации
и размещению значений в регистрах.

## Наблюдения на LLVM 21.1.8

Для Linux x86-64, с системным GCC 14.2.0 и указанными выше настройками:

| `grow` | Инструкции IR | `alloca` | `load` | `store` |
| --- | ---: | ---: | ---: | ---: |
| raw | 33 | 5 | 10 | 7 |
| mem2reg | 20 | 1 | 4 | 4 |
| sroa + mem2reg | 5 | 0 | 0 | 0 |
| O2 | 5 | 0 | 0 | 0 |

`mem2reg` убирает часть локальных переменных, но хранение полей структуры
в памяти остаётся. После SROA структура представлена двумя значениями SSA.
Тело `grow` содержит две операции `fadd`, две сборки результата `insertvalue`
и `ret`; локальное хранилище больше не нужно.

В `local_sum` после SROA остаются 22 инструкции, включая вызов `grow`,
без `alloca`, `load` и `store`. После O2 вызов встроен, а цикл развёрнут
на четыре итерации с обработкой остатка. В теле уже 49 инструкций.
Такой рост размера не означает замедление: статическое число инструкций
не учитывает частоту выполнения и стоимость операций.

| `dispatch_sum` | Инструкции IR | `alloca` | `load` | `store` | Косвенные вызовы |
| --- | ---: | ---: | ---: | ---: | ---: |
| raw | 77 | 11 | 20 | 12 | 1 |
| mem2reg | 58 | 5 | 12 | 7 | 1 |
| sroa + mem2reg | 37 | 0 | 4 | 0 | 1 |
| O2 | 27 | 0 | 4 | 0 | 1 |

Оптимизации убирают локальные временные объекты и агрегатные копии.
В O2 остаются четыре загрузки: указатель на фигуру, указатель на таблицу,
тег специализации и адрес обработчика. Вызов обработчика остаётся косвенным:

```llvm
%r38 = tail call double %r33(ptr nonnull %r17, double %a2_0, double %a2_1)
```

В этом примере таблица изменяется при runtime-регистрации, а `dispatch_sum`
работает с обобщёнными указателями. Обычный O2 не превращает этот вызов в
прямой. Это наблюдение относится к данной программе и её IR; специализированные
и замкнутые сценарии требуют отдельного исследования.

По всему модулю число `alloca` меняется как `53 → 23 → 3 → 3`.
После O2 косвенных точек вызова в модуле становится две: встраивание
`dispatch_sum` создаёт такую точку также в `main`, а публичное тело исходной
функции сохраняется. Счётчик точек вызова не равен числу вызовов при выполнении.

На LLVM 19.1.7 для этого исходника получены те же приведённые счётчики и
результаты выполнения. Набор проходов `default<O2>` зависит от версии LLVM;
совпадение этих чисел не означает тождественности всех преобразований.

## Как изучать результат

```sh
diff -u build/llvm-opt-demo/raw/grow.txt build/llvm-opt-demo/mem2reg/grow.txt
diff -u build/llvm-opt-demo/mem2reg/grow.txt build/llvm-opt-demo/sroa/grow.txt
diff -u build/llvm-opt-demo/sroa/local_sum.txt build/llvm-opt-demo/O2/local_sum.txt
cat build/llvm-opt-demo/O2/dispatch_sum.txt
```

`diff` возвращает 1, если файлы различаются; при таком сравнении это ожидаемо.
Полный IR позволяет проследить загрузку таблицы и вызов, а `program.s` —
посмотреть получившийся машинный код. Для повторения одного преобразования
вручную, например:

```sh
opt -S -mcpu=x86-64 -passes='function(sroa,mem2reg)' -verify-each \
  build/llvm-opt-demo/input.bc -o build/llvm-opt-demo/manual-sroa.ll
```

`metrics.tsv` считает статические инструкции по тексту IR этого примера.
Прямые вызовы не включают LLVM intrinsics; отдельный столбец учитывает
`llvm.memset`, `llvm.memcpy` и `llvm.memmove`. Числа не используются как
условия прохождения теста: при смене версии LLVM корректный IR может иметь
другую форму. Корректность выполнения проверяется независимо.

Первый результат исследования: форма IR с локальными объектами в памяти
поддаётся стандартным проходам SROA/SSA, включая агрегатный ABI. Следующее
направление — сравнить диспетчеризацию для заранее известной специализации,
закрытого обобщения и открытого межмодульного набора обработчиков.
