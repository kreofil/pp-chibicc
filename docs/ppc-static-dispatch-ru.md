# Статические таблицы в явно закрытой LLVM-программе

Утилита `cmake/ppc-static-dispatch.py` строит конечные таблицы обработчиков
после [межмодульного анализа](ppc-dispatch-report-ru.md). Преобразуются только
функции, у которых **закрыты все процедурные типы** и для каждой комбинации
известен единственный обработчик с определением.

Передаются все пользовательские LLVM-модули и опция `--closed-program`.
Утилита проверяет состав, регистрации и обращения к таблицам, затем формирует
один `.ll` для конечной программы. Обычная раздельная сборка сохраняет
runtime-таблицы и регистрацию.

Для повседневной сборки доступна [опция компилятора `--closed-program` и
модуль CMake](llvm-closed-compiler-ru.md). Приведённые ниже ручные команды
сохраняются для исследования промежуточного IR.

## Готовый пример

Нужны Python 3.8+ и `llvm-as`, `opt`, `llc`, `llvm-link` одной major-версии,
не ниже 19. Для LLVM 23:

```sh
cmake -S . -B build -DPPCHIBICC_LLVM_VERSION=23
cmake --build build --target llvm-static-dispatch-demo
cat build/llvm-static-dispatch-demo/report.md
```

Альтернатива: `make llvm-static-dispatch-demo`. Цель
`test-llvm-static-dispatch-stage2` проверяет самокомпилированный компилятор.

Пример [closed-registry](../examples/llvm/closed-registry) состоит из трёх
модулей. Матрица `2×3` содержит два конкретных обработчика и четыре ячейки
общего обработчика. Удаляются 11 функций поддержки именно этой таблицы:
выделение, регистрация, проверки полноты и освобождение из всех модулей.
Вместо них создаются неизменяемый массив адресов и внутренний константный
указатель на него. Выбранные обработчики получают внутреннее связывание.

Вызов с известными специализациями после `default<O2>` сокращается до:

```llvm
define i32 @registry_known() {
  ret i32 507
}
```

В runtime-варианте здесь остаётся косвенный вызов. Динамические признаки
продолжают индексировать неизменяемый массив. Защитные сравнения уже
сформированного `switch` обрабатываются обычными проходами LLVM; устранение
всех сравнений для любого динамического индекса этим этапом не гарантируется.
Это наблюдение по IR, а не измерение быстродействия.

## Своя программа

```sh
mkdir -p build/static-input
for unit in main special default; do
  bin/ppchibicc -S -emit-llvm examples/llvm/closed-registry/$unit.c \
    -o build/static-input/$unit.ll
done

python3 cmake/ppc-static-dispatch.py --closed-program \
  --family registry_combine \
  build/static-input/main.ll \
  build/static-input/special.ll \
  build/static-input/default.ll \
  -o build/static-program.ll --report build/static-program.json

bin/ppchibicc --backend=llvm -O2 build/static-program.ll -o build/static-program
build/static-program
```

Ожидается `closed registry OK`. `--family` можно повторять; без него выбираются
все подходящие функции. Открытые функции и неразрешённые закрытые матрицы
остаются на runtime-пути. Явное требование неподходящей функции даёт ошибку.

Пути к инструментам задаются через `--llvm-as`, `--llvm-opt`, `--llvm-link`
или `PPCHIBICC_LLVM_AS`, `PPCHIBICC_LLVM_OPT`, `PPCHIBICC_LLVM_LINK`.
По умолчанию используются имена из PATH. `--entry` задаёт точку входа
(по умолчанию `main`), её определение должно входить в IR. `--max-cells`
ограничивает каждую статическую таблицу; по умолчанию 4096 ячеек, независимо
от предела локальной оптимизации `switch`.

## Проверка полноты сведений

- Каждый вход — отдельный исходный `.ll` ppchibicc или помеченный IR-объект
  `--closed-program -c` со схемой v2, собственным
  именем исходника и маркером единицы. Повторные единицы, уже объединённый или
  оптимизированный IR и native-объекты отклоняются. Проверяются целевая
  Linux x86-64 платформа и раскладка данных.
- Закрытые оси и ABI согласованы; все ячейки и определения известны.
  Конкретный обработчик приоритетнее общего. Для разных конкретных регистраций
  одной координаты произвольный победитель не выбирается.
- Метаданные описывают все функции выделения, регистрации, проверки и
  освобождения. Проверяются их определения, владение таблицей и фактические
  записи в массивах конструкторов/деструкторов с ожидаемыми приоритетами.
- Остальные функции только читают таблицу. Запись в указатель или ячейки,
  сохранение/передача её адреса и посторонние вызовы удаляемых конструкторов
  препятствуют преобразованию.
- Все пользовательские зависимости входят в IR. Неопределённые символы
  допускаются для поддерживаемых функций C/POSIX runtime и LLVM-интринсиков.
  Неизвестная внешняя функция требует включить её модуль.

Первый вариант предназначен для конечного исполняемого файла. Набор внешних
функций перечислен в `C_FUNCTIONS` утилиты: выделение памяти, печать, строки,
файлы, `qsort`, математические функции и другие указанные операции. Загрузка
модулей через `dlopen`/`dlsym` и произвольные native-библиотеки приложения в
этот режим не входят.

`--closed-program` утверждает полноту пользовательского состава; утилита не
обнаруживает автоматически все возможные библиотеки. Добавление модуля с
обработчиками требует повторного построения из полного набора IR. Для
расширяемой сборки остаётся обычный runtime-путь.

## Результат и совместимость

JSON сохраняет входные файлы и SHA256, матрицы, удалённые функции поддержки,
оставшиеся внешние символы и контрольную сумму выходного IR. Поле
`program_completeness: "explicit-input-set"` фиксирует явно заданный состав;
его хеш записывается также в `!ppchibicc.closed_program`. Выход проверяется
`llvm-as` и LLVM verifier до публикации. Ошибка проверки сохраняет прежние
выходные файлы.

Для интеграции с компилятором предусмотрены `--quiet` и `--allow-empty`:
первая опция подавляет сообщение об успехе, вторая разрешает программу без
подходящих таблиц, сохраняя проверки входных модулей, точки входа и внешних
зависимостей. Без `--allow-empty` отсутствие подходящих таблиц остаётся ошибкой.

Схема `ppchibicc.dispatch.v2` добавляет описания runtime-функций. Утилита
отчёта читает v1 и v2; преобразованию нужна v2. Обычный ABI 4П и числовые
индексы этим этапом не меняются.

Доступ к сгенерированным таблицам выражается байтовым LLVM `getelementptr`
без `inbounds`, чтобы LLVM мог раскрывать константные ячейки. Обычная
C-арифметика указателей/целых сохраняет прежнее понижение.
Признаки, `get_spec_ptr` и инициализация глобальных объектов сохраняют свою
необходимую поддержку. Не выбранные функции продолжают использовать свои
runtime-таблицы и проверки.

Для сравнения четырёх представлений добавлен
[бенчмарк закрытых мультиметодов](llvm-static-dispatch-benchmark-ru.md):
динамические признаки, равномерные/смещённые данные, короткие/вычислительные
обработчики, общий таймер, статистика времени и размеры машинного кода.
