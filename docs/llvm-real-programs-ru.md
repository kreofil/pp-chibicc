# Проверка реальных программ 4П через LLVM

Цель `llvm-real-programs` сравнивает три программы из
[`kreofil/4P-examples`](https://github.com/kreofil/4P-examples) в пяти режимах:
прямой x86-64 backend, обычный LLVM O0/O2 и `--closed-program` O0/O2.
Исторический закрытый `spec-param` дополнительно проверяется как отрицательный
случай. Актуальный открытый пример из `examples/simplest/spec-param/main.c`
с пользовательским обработчиком `Figure.void` проверяется как успешный,
в том числе с явным вызовом нулевого обработчика. На каждый компилятор
приходится 30 сборок и запусков: 25 успешных и 5 ожидаемых остановок
исторического примера с диагностикой до `main`.

## Запуск

Нужны Python 3.8+, GNU `size`, системный C toolchain и `llvm-as`, `opt`,
`llc`, `llvm-link` одной major-версии, не ниже 19. Проверены 19.1.7,
21.1.8 и 23.1.6. Например, с LLVM 23:

```sh
cmake -S . -B build -DPPCHIBICC_LLVM_VERSION=23
cmake --build build --target llvm-real-programs
cat build/llvm-real-programs/report.md

cmake --build build --target test-llvm-real-programs-stage2
```

Обе цели входят в LLVM CI. Для повторяемости в репозитории сохранён
неизменённый набор необходимых исходников из commit
[`9e8f1f1`](https://github.com/kreofil/4P-examples/commit/9e8f1f1c07ef08e845f877c8dac7a804ef9c0af4).
Файл `examples/llvm/real-programs/upstream.json` содержит пути и SHA256.
Доступ к сети для тестовых целей не нужен. Существующие CMake-файлы проектов
из `4P-examples` для этих проверок не используются и не меняются.

## Что именно проверяется

### Специализированные обычные параметры и результаты

[`simplest/spec-param/main.c`](https://github.com/kreofil/4P-examples/blob/9e8f1f1c07ef08e845f877c8dac7a804ef9c0af4/ppc-new-syntax/simplest/spec-param/main.c)
содержит закрытое `Figure`, обработчики треугольника и прямоугольника,
передачу специализации по указателю/значению, возврат специализированной
структуры и полиморфные вызовы через обычные параметры.

Закреплённый исторический пример из `4P-examples` компилируется, но каждый
backend останавливает его до `main`:

```text
PPC completeness error: missing handler for Print table slot 0
```

Для закрытой матрицы нужна также нулевая координата `Figure.void`.
Это требование существующего протокола полноты, а не ошибка поддержки
специализаций в обычных параметрах. Пример содержит старый комментарий
о такой ошибке; саму передачу параметров текущий ppchibicc поддерживает.

Отдельный адаптер `spec-param-covered.c` добавляет явный обработчик
`Figure.void`, вызывает его и затем выполняет исходный `main`.
Оригинал сохранён без изменений. Эталон проверяет все 13 строк, в том числе
возврат `Rectangle(100,20)` по значению. В этой версии закрытая сборка
выбирает `Print`, формирует константную таблицу из трёх адресов и удаляет
шесть функций поддержки таблицы.

Для исходного неполного варианта `--closed-family=Print` дополнительно
проверяется как ошибка сборки. Без явного требования семья остаётся
runtime-семьёй и обнаруживает пропуск до `main`.

### Актуальный spec-param из ppchibicc

В `examples/simplest/spec-param/main.c` добавлен обработчик `Figure.void`.
Этот пример проверяется без изменений как `spec-param-current` во всех
пяти режимах. Отдельный `spec-param-current-zero.c` только переименовывает
его `main`, вызывает собственный нулевой обработчик примера и затем исходный
`main`; дополнительного обработчика он не определяет.

В актуальной версии `Figure` открыт и расширяется через `+`, поэтому семья
`Print` должна остаться `excluded`, даже при `--closed-program`. Это отдельная
проверка от исторического закрытого варианта. Проверяются 12 обычных строк
и дополнительная строка нулевого обработчика с индексом 0.

### Открытый мультиметод-посетитель

[`visitor-mm.ppc`](https://github.com/kreofil/4P-examples/blob/9e8f1f1c07ef08e845f877c8dac7a804ef9c0af4/ppc-new-syntax/patterns/shvets-patterns/visitor-mm.ppc)
содержит открытые `Component` и `Visitor`, две специализации каждого типа,
создание объектов через `create_spec`, массив обобщённых указателей и
четыре комбинации вызовов `VisitComponent`.

Текст сверяется с явно заданным эталоном. При закрытой сборке исходные типы
остаются открытыми, отчёт классифицирует семью как `excluded`, статические
таблицы не создаются. Проверяется сохранение runtime-пути при объединении IR.

### Многомодульный ppVector

[`ppvector-sum-int`](https://github.com/kreofil/4P-examples/blob/9e8f1f1c07ef08e845f877c8dac7a804ef9c0af4/ppc-new-syntax/containers/vector-list-lib/examples/ppvector-sum-int/ppvector-sum-int.c)
собирается вместе с `ppvector.c` и `ppgeneral.c`. Проверяются заполнение
вектора числами 10..1, сумма 55, сортировка 1..10 и состояние после удаления
буфера. Эталон вычисляется Python-кодом независимо от native-вывода.

Проверка выявила отсутствовавшую в списке допустимых внешних runtime-функций
операцию `reallocarray`. Она добавлена; отдельный тест проверяет создание,
увеличение буфера с сохранением данных и отказ при переполнении произведения
размеров с сохранением исходного буфера и `errno == ENOMEM`.

Обобщения вектора открыты, поэтому `--closed-program` объединяет их IR,
но не замораживает таблицы. Библиотечные модули передаются непосредственно
в составе программы: поддержка native-архивов в закрытом режиме не добавлялась.

## Наблюдения о размере кода

Локальный запуск на Linux x86-64 с LLVM 23.1.6 дал следующие размеры `.text`
всего исполняемого файла, в байтах:

| Программа | x86-64 | LLVM O0 | LLVM O2 | Закрытая O0 | Закрытая O2 |
| --- | ---: | ---: | ---: | ---: | ---: |
| spec-param с нулевым обработчиком | 4647 | 3558 | 2328 | 3102 | 1634 |
| visitor-mm | 6150 | 3191 | 1452 | 3194 | 1437 |
| ppvector-sum-int | 15135 | 7731 | 3602 | 7741 | 3910 |

Во всех успешных вариантах совпадают проверяемые результаты. Статическая
таблица `Print` уменьшает код в данном примере. У открытого вектора общий
O2 дал больший `.text`, чем отдельный O2 модулей: межмодульная оптимизация
не гарантирует уменьшения размера. В измерение входят startup/runtime-функции;
другой toolchain может дать другие числа.

Время выполнения этих коротких программ с печатью не измеряется.
Полученные размеры не доказывают ускорения; для измерения времени нужен
отдельный достаточно длительный вычислительный сценарий. Такой запуск
добавлен для [ядра «Жизни»](llvm-life-benchmark-ru.md).

## Артефакты и внешний репозиторий

Каждый запуск создаёт новый подкаталог `run-*`. В нём сохраняются исходники,
исходный IR каждой единицы, объединённый IR, матрицы и манифесты закрытой
сборки, исполняемые файлы, команды в JSON и stdout/stderr каждой операции.
`report.json` содержит версии инструментов, SHA256 исходников, компилятора
и программ, секции ELF, результаты всех вариантов и причины исключения семей.
Верхние `report.md` и `report.json` указывают на последний успешный запуск.

Можно проверить те же пути непосредственно в своей копии `4P-examples`:

```sh
python3 cmake/llvm-real-programs.py \
  --source-dir "$PWD" --compiler "$PWD/bin/ppchibicc" \
  --llvm-as llvm-as --llvm-opt opt --llvm-llc llc --llvm-link llvm-link \
  --examples-dir /path/to/4P-examples --result-dir build/llvm-real-external
```

Для внешней копии сохраняются её Git HEAD, фактические хеши выбранных файлов
и их совпадение с закреплённой версией. Изменённый набор всё равно должен
удовлетворять явно заданным ожидаемым результатам и проверкам матриц.
Поддержка новых путей или другого поведения требует отдельного изменения
описания проверяемого примера.
