# Пустые списки параметров C и 4П

LLVM backend ppchibicc поддерживает пустую запись `()` в объявлениях,
определениях и типах указателей на функции. Определения `int f() { ... }`
и `int main() { ... }` компилируются без обязательного `(void)`.

## Запись сигнатуры и вызова

Обычную функцию можно записать как `int main()` или `int main(void)`.
Для 4П процедурные
параметры остаются в отдельном списке `<...>`:

```c
double FigurePerimeter<Figure *f>();
double FigurePerimeter<Figure.rect *f>(void) {
  return RectanglePerimeter(&f->rect);
}

// Вызов в теле функции:
// double perimeter = FigurePerimeter<figure>();
```

У функций 4П `()` и `(void)` означают отсутствие **обычных** параметров
и взаимозаменяемы в объявлениях, определениях и обработчиках, включая разные
единицы трансляции. Объект `figure` передаётся через список параметров 4П,
как прежде. Вызов содержит пустые скобки.

## Объявления обычных C-функций

В модели C11/C17 объявление `f()` оставляет типы обычных параметров
неуказанными. Это позволяет объявить функцию до определения с параметрами:

```c
double calculate();
double caller(void) { return calculate(1.25f, (short)7); }
double calculate(double x, int n) { return x + n; }
```

Вызов без прототипа продвигает `float` в `double`, `_Bool`, `char` и `short`
в `int`. LLVM backend поддерживает такие скалярные вызовы, в том числе через
указатели и к функциям, собранным GCC/Clang. Последующий прототип уточняет
тип функции; последующее объявление `f()` сохраняет уже известный прототип.
При совместимости с `f()` учитываются продвижения: прототип с `double`/`int`
допустим, с `float`/`char` — нет. Определение `f() { ... }` содержит ноль
параметров, поэтому конфликтует с прототипом, требующим аргументы.

`f(void)` остаётся явным прототипом без параметров и диагностирует лишние
аргументы. Эта модель соответствует C11/C17; версия установленных LLVM-
инструментов её не меняет.

Настоящие вариадические определения с `...` пока диагностируются как
`LLVM backend: variadic function definitions is not supported yet`.
Внешние вариадические вызовы вроде `printf` сохраняют свою поддержку.
Передача агрегата при отсутствии прототипа также пока диагностируется:
для такого аргумента нужен фиксированный прототип. Возврат малых и крупных
структур из функций с пустым `()` поддерживается. Определения K&R с именами
параметров в скобках и объявлениями их типов после скобок сюда не входят.

## Представление в LLVM

Пустое определение C-функции получает фиксированную сигнатуру IR:

```llvm
define i32 @answer() {
  ret i32 42
}
```

У объявления C-функции без прототипа и вызова с ещё не указанными типами
используется вариадическая запись LLVM:

```llvm
declare double @calculate(...)
; В теле вызывающей функции:
; %r = call double (...) @calculate(double 1.25, i32 7)
```

Это представление неопределённых типов параметров отделено от исходного
`...`: frontend хранит отдельные признаки `is_unprototyped` и `is_variadic`.
У функций 4П обычный пустой список сразу задаёт ноль обычных параметров,
а процедурные указатели входят в фиксированную сигнатуру.

Семантика диспетчеризации 4П, расположение тегов, таблицы обработчиков
и регистрация сохраняются; используется прежний System V ABI.

## Проверки

```sh
cmake -S . -B build-llvm23 -DPPCHIBICC_LLVM_VERSION=23
cmake --build build-llvm23 --target test-all test-llvm test-llvm-stage2
```

Проверено на LLVM 19.1.7, 21.1.8 и 23.1.6 при O0/O2; stage2 проверен с LLVM 23.
Общие native/stage2 тесты `test/empty-params.c` и `test/ppc-empty-params.c`
включены также в LLVM-набор. Проверены рекурсия, указатели на функции,
совместимость и уточнение прототипов, скалярные продвижения, малые/крупные
результаты-структуры, мультиметоды и строгое enum-обобщение. Независимый
модуль GCC/Clang проверяет ABI-вызовы в обе стороны. Межмодульный набор
смешивает `()` и `(void)` у native/LLVM-объектов. Истинные вариадические
определения и агрегатные аргументы без прототипа покрыты диагностическими тестами.

`test-all` сохраняет native-проверки и самокомпиляцию.
`test-llvm` и `test-llvm-stage2` также запускают все
восемь этапов `evolution/figures/evo-reuse-code` при O0/O2 и сравнивают
полученные файлы с эталонами. Это проверяет раздельную компиляцию объявлений,
обобщающих функций и обработчиков, включая повторное использование
`FigurePerimeter` на этапах 03 и 08.

Общий `cmake/run-example-tests.sh` принимает дополнительные аргументы
компилятора после первых двух параметров; списки файлов и эталоны одинаковы
для native- и LLVM-прогонов.

Дополнительно native- и LLVM O0/O2-программы дали одинаковые результаты:
пример потоков получил периметры 16, 22 и 28; adapter совпал со своим
эталоном; модули карт плоскости и тора проверены отдельным конечным запуском
`DrawMap` и `LivingCells` на сетке 3 × 3. Интерактивный цикл игр не запускался.

Повторить аудит CMake-проектов можно отдельно:

```sh
python3 cmake/audit-llvm-examples.py --compiler "$PWD/bin/ppchibicc" \
  --output build-llvm-example-audit-void
cat build-llvm-example-audit-void/report.md
```

`opt` и `llc` выбираются через `PATH` либо экспортированные
`PPCHIBICC_LLVM_OPT`/`PPCHIBICC_LLVM_LLC`. Результат от 2026-11-11, до
добавления автоматического распознавания `.ppc`:

| Результат | До согласования | После |
| --- | ---: | ---: |
| Успешная LLVM O2 сборка CMake-проекта | 15 | 23 |
| Совпавший выходной эталон фигур в аудите | 12 | 15 |
| Ошибка LLVM на пустых списках параметров | 8 | 0 |
| Ошибка CMake-настроек при обоих backend | 15 | 15 |

Все восемь прежних ошибок сигнатур устранены. Числа относятся к 38 полным
CMake-проектам; успешная сборка игры не означает проверку её интерактивного
цикла. Автоматическое распознавание `.ppc` теперь устраняет необходимость
`-x c` для этого расширения. В оставшихся CMake-проектах нужно согласовать
`LANGUAGE C` для реализаций и исключить заголовки `.pph`/`.h` из отдельной компиляции,
как описано в [инструкции компилятора](llvm-compiler-ru.md#файлы-ppc-и-pph).
