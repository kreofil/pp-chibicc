# Межмодульный отчёт о закрытой диспетчеризации

Это первый этап подготовки статических таблиц мультиметодов. LLVM-компилятор
сохраняет описание закрытых функций 4П в IR, а отдельная утилита собирает
матрицы обработчиков из нескольких модулей. Отчёт помогает проверить модель
регистрации перед заменой динамической таблицы статической.

Фиксированные координаты описываются **только когда закрыты все процедурные
типы функции**. Открытое или непрозрачное объявление отмечается как исключение.
Текущие runtime-таблицы, конструкторы и защищённые вызовы продолжают работать;
этот этап добавляет сведения для анализа и не меняет ABI.

## Готовый пример

Нужны Python 3.8+ и `llvm-as`, `opt`, `llc`, `llvm-link` одной major-версии,
не ниже 19. С установленной LLVM 23:

```sh
cmake -S . -B build -DPPCHIBICC_LLVM_VERSION=23
cmake --build build --target llvm-dispatch-report
cat build/llvm-dispatch-report/report.md
```

Альтернатива: `make llvm-dispatch-report`. Цель также выполняет проверки
метаданных. Для самокомпилированного компилятора:

```sh
cmake --build build --target test-llvm-dispatch-report-stage2
```

Исходники находятся в [examples/llvm/closed-registry](../examples/llvm/closed-registry):
`main.c` вызывает мультиметод, `special.c` определяет два конкретных
обработчика, `default.c` — общий. Все шесть порядков объектных файлов дают
`closed registry OK`.

Закрытые типы имеют размеры 2 и 3, включая нулевые альтернативы. В отчёте
получается следующая матрица:

| Индекс | Первый аргумент | Второй аргумент | Обработчик |
| ---: | --- | --- | --- |
| 0 | `RegistryLeft.void` | `RegistryRight.void` | Конкретный для `(0, 0)` |
| 1 | `RegistryLeft.void` | `RegistryRight.one` | Общий |
| 2 | `RegistryLeft.void` | `RegistryRight.two` | Общий |
| 3 | `RegistryLeft.one` | `RegistryRight.void` | Общий |
| 4 | `RegistryLeft.one` | `RegistryRight.one` | Общий |
| 5 | `RegistryLeft.one` | `RegistryRight.two` | Конкретный для `(1, 2)` |

В каталоге результата сохраняются `report.md`, `report.json`, отдельные и
объединённые `.ll`, bitcode, объекты и исполняемые проверки.

## Свои модули

Сначала сформируйте LLVM IR каждой единицы трансляции:

```sh
mkdir -p build/registry-input
for unit in main special default; do
  bin/ppchibicc -S -emit-llvm examples/llvm/closed-registry/$unit.c \
    -o build/registry-input/$unit.ll
done

python3 cmake/ppc-dispatch-report.py \
  build/registry-input/main.ll \
  build/registry-input/special.ll \
  build/registry-input/default.ll \
  --json build/registry-input/report.json \
  --markdown build/registry-input/report.md \
  --require-resolved
```

Подходит также объединённый текстовый IR после `llvm-link -S`. Для bitcode
сначала получите текст: `opt -S -passes=verify input.bc -o input.ll`.
Утилита читает метаданные из `.ll` и не требует Python-пакетов либо библиотек
LLVM. Исходный режим `-S -emit-llvm` формирует метаданные без внешних инструментов.

Порядок переданных файлов не выбирает победителя между разными конкретными
регистрациями. Такие случаи явно отмечаются как зависящие от порядка;
утилита не подменяет действующее поведение runtime произвольным выбором.

## Состояния

| Состояние | Значение |
| --- | --- |
| `resolved` | Для каждой ячейки найден единственный обработчик с определением среди переданных метаданных и с телом в IR |
| `incomplete` | Есть комбинации без конкретного или общего обработчика |
| `blocked` | Есть открытое/непрозрачное объявление этой функции в участвующем модуле, отсутствуют определения либо обнаружены противоречивые регистрации |
| `order-dependent` | Для ячейки имеются разные конкретные обработчики или несколько общих обработчиков свободных ячеек |
| `inconsistent` | Модули расходятся в описании закрытых типов, LLVM ABI или символа таблицы |
| `limited` | Матрица превышает предел развёртывания отчёта |
| `excluded` | Для функции доступны только открытые/непрозрачные объявления; закрытая матрица не строится |

Конкретные обработчики имеют приоритет перед общими. Повторное внешнее
объявление одного символа не считается новым обработчиком; требуется его
определение в переданных сведениях. Одинаковые имена частных функций из разных
единиц трансляции обозначают разные обработчики.

По умолчанию отчёт разворачивает до 4096 ячеек на функцию; предел задаётся
через `--max-cells`. Он независим от предела 16 ячеек локальной оптимизации
`switch`: анализировать можно и большие закрытые таблицы.

Код завершения 0 означает успешное построение отчёта. Опция
`--require-resolved` возвращает 1, если хотя бы одна включённая закрытая
функция имеет другое состояние; отчёт при этом сохраняется. Исключённые
открытые функции остаются перечислены отдельно. Ошибка входных данных или
неподдерживаемая версия метаданных возвращает 2.

## Что содержится в LLVM

Именованные метаданные `!ppchibicc.dispatch` используют схему
`ppchibicc.dispatch.v2` (утилита читает также v1) и включают:

- `unit`: исходную единицу трансляции, в том числе для обычного C-модуля;
- `family`: имя функции, её пониженный LLVM ABI, арность и ссылку на таблицу;
- `axis`: имя и вид закрытого типа, размер/выравнивание, число и порядок альтернатив;
- `handler`: конкретные координаты либо общий обработчик, ссылку на функцию,
  признаки определения и частного связывания;
- `excluded`: имя функции с открытым или непрозрачным процедурным типом.
- `runtime` (v2): роль и ссылку на функцию поддержки таблицы для проверки
  её регистрации перед статическим преобразованием.

Ссылки на таблицы и функции являются LLVM-операндами `ptr`, поэтому
`llvm-link` обновляет их при переименовании внутренних символов. Строки
экранируются побайтово, включая кавычки и UTF-8. Сведения об определениях
проверяются по наличию тел в переданном IR; удалённая ссылка или отсутствующее
тело не дают состояния `resolved`.

## Граница этого этапа

`resolved` относится к **перечисленным модулям**. Это ещё не доказательство,
что в программу не войдут другие LLVM/native-объекты, архивы или регистрации.
Поэтому JSON явно содержит `program_completeness: "not-established"` и
`optimization_applied: false`. Для явно заданной конечной программы добавлен
отдельный [режим статических таблиц](ppc-static-dispatch-ru.md), который
проверяет регистрации и обращения к таблицам перед преобразованием.

Проверки покрывают все четыре вида типов, матрицы нескольких размерностей,
ранний/поздний общий обработчик, объявления с внешними определениями,
отсутствующие ячейки и тела, разные частные регистрации, противоречивые типы
и ABI, непрозрачные модули, переименование при `llvm-link`, bitcode/O2,
экранированные имена файлов и сохранение отчёта при некорректном вводе.
