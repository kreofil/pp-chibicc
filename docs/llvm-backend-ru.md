# Экспериментальный backend LLVM IR

Режим `-S -emit-llvm` выводит текстовый LLVM IR для небольших программ на C
и первых процедурно-параметрических примеров. Обычная сборка ppchibicc не требует библиотек
LLVM. Для проверки IR, оптимизации и получения исполняемого файла используются
внешние инструменты LLVM одной версии. Текущая целевая линия — LLVM/Clang
23.1.x. Полные проверки выполнены на 23.1.6; ранее проверены LLVM 19.1.7 и 21.1.8.

Целевая платформа первого backend — Linux x86-64 с ABI System V. Применение
другого `target triple` само по себе не переносит frontend на другую платформу.

Для обычной сборки используйте [режим `--backend=llvm`](llvm-compiler-ru.md).
Компилятор сам вызывает `opt` и `llc` и формирует `.o`, ассемблер или
исполняемый файл. Пример:

```sh
bin/ppchibicc --backend=llvm -O2 examples/llvm/hello.c -o build/hello
build/hello
```

Ниже сохранены ручные команды для изучения отдельных стадий. Режим
`-S -emit-llvm` по-прежнему выводит исходный IR без внешних LLVM-инструментов.

## Первый пример

Из корня репозитория после обычной сборки:

```sh
bin/ppchibicc -S -emit-llvm examples/llvm/hello.c -o build/hello.ll
llvm-as build/hello.ll -o build/hello.bc
opt -passes=verify -disable-output build/hello.bc
opt -S -passes='default<O2>' -verify-each build/hello.bc -o build/hello.O2.ll
llc -O=2 -filetype=obj -relocation-model=pic build/hello.O2.ll -o build/hello.o
cc build/hello.o -o build/hello
build/hello
```

Ожидаемый вывод:

```text
Hello from ppchibicc LLVM IR
```

Команды приведены без суффиксов версий, например для LLVM 23, выбранного через
`PATH`. Если в системе используются имена `llvm-as-23`, `opt-23` и `llc-23`,
следует подставить их вместо команд без суффиксов. Версии инструментов должны
совпадать.

## Первый пример 4П

`examples/llvm/ppc-figures.c` задаёт обобщение `Figure`, специализации
прямоугольника и квадрата, общий обработчик и два конкретных обработчика
функции `Perimeter`. Обобщённый указатель определяет обработчик при выполнении.

```sh
bin/ppchibicc -S -emit-llvm examples/llvm/ppc-figures.c -o build/ppc-figures.ll
llvm-as build/ppc-figures.ll -o build/ppc-figures.bc
opt -S -passes='default<O2>' -verify-each build/ppc-figures.bc -o build/ppc-figures.O2.ll
llc -O=2 -filetype=obj -relocation-model=pic build/ppc-figures.O2.ll -o build/ppc-figures.o
cc build/ppc-figures.o -o build/ppc-figures
build/ppc-figures
```

Ожидаемый вывод:

```text
figure 1: perimeter=14
figure 2: perimeter=20
```

Пустой список обычных параметров можно записывать как `()` или `(void)`,
например `int Perimeter<Figure *f>()`. Для обычного C поддерживаются
определения `f()` без параметров, объявления без прототипа и скалярные
вызовы через них с продвижениями C11/C17. Вариадические определения с `...`
поддерживают скалярные аргументы и стандартный `stdarg`. Правила пустых списков описаны в
[руководстве по безаргументным сигнатурам](llvm-void-signatures-ru.md).

## Структуры по значению

`examples/llvm/ppc-by-value.c` показывает обычную функцию `enlarge`, которая
принимает и возвращает `Rectangle`, и обобщающую функцию `describe`, которая
принимает `Rectangle` как обычный параметр и возвращает `Report`.

```sh

llvm-as build/ppc-by-value.ll -o build/ppc-by-value.bc

cc build/ppc-by-value.o -o build/ppc-by-value
build/ppc-by-value
```

Ожидаемый вывод:

```text
kind 1: 7 x 9
kind 2: 9 x 10
```

## Вещественные вычисления и 4П

`examples/llvm/ppc-floating.c` хранит размеры фигур в полях `double`.
Обобщающая функция `Area` принимает обычный параметр `double scale`, выбирает
обработчик по обобщённому указателю и возвращает площадь типа `double`.
Вывод через `printf` проверяет также передачу вещественных аргументов в `...`.

```sh
build/ppc-floating
```

Ожидаемый вывод:

```text
figure 1: area=10.00, scaled=40.00
figure 2: area=12.25, scaled=49.00
```

## Выбор режима вывода

Без `-o` результат записывается в текущем каталоге с именем исходного файла
и расширением `.ll`.
Параметр `-o -` направляет IR в стандартный вывод. Для `.ppc` язык определяется
автоматически, как для `.c`; для других расширений можно указать `-xc`.
Режим требует `-S`; сочетания с `-c`, `-E`
или `-M` отклоняются. Генерация IR не запускает `opt` или `llc` автоматически.

## Поддерживаемое подмножество

Поддерживаются целочисленные типы C, `_Bool`, `float`, `double` и `long double`, указатели,
массивы фиксированной и переменной длины, локальные и глобальные переменные, строковые
литералы, обычные функции с фиксированными прототипами, арифметика и сравнения,
ветвления, циклы,
короткое вычисление `&&`/`||` и условное выражение `?:`.

Для `float`, `double` и `long double` поддерживаются арифметика, сравнения, преобразования
между ними и целочисленными типами, прямые и косвенные вызовы функций.
Константы кодируются точно в шестнадцатеричной форме LLVM. Операции сохраняют
знаковый ноль и поведение сравнений с NaN; NaN в условии и при преобразовании
к `_Bool` даёт истину. IR не использует флаги `fast-math`.
Скалярные вещественные параметры используют отдельные регистры SSE и не
расходуют целочисленные регистры при расчёте ABI структур.

Структуры и объединения поддерживаются в памяти: локальные и глобальные
объекты, вложенные поля, массивы, инициализация, присваивание и работа через
указатели. Сохраняются размеры, смещения и выравнивание, рассчитанные frontend.
Скалярные поля могут быть целочисленными, указателями, `float`, `double` или `long double`.
Такие структуры и объединения можно передавать и возвращать по значению,
в том числе через указатели на функции и обычные параметры функций 4П.

Для ABI System V значения размером до 16 байт разбиваются на восьмибайтовые
части классов INTEGER и SSE. Если в одной части совмещаются целочисленные
и вещественные поля, используется INTEGER. Для объединений учитываются все
перекрывающиеся варианты. Части SSE передаются через `float`, `double` или
LLVM-тип `<2 x float>`: пара `float` занимает один XMM-регистр.
Части, содержащие только padding, регистров не расходуют.

Учитываются шесть целочисленных и восемь SSE-регистров параметров. Если
структуре не хватает регистров хотя бы одного класса, весь аргумент передаётся
через память, а регистры остаются доступными следующим аргументам.
Крупные и невыровненные значения используют `byval`, результаты — скрытый
параметр `sret`. Эти атрибуты согласованы в объявлениях, определениях и вызовах;
их назначение описано в [LLVM Language Reference](https://llvm.org/docs/LangRef.html#parameter-attributes).
Перед вызовом создаётся копия аргумента, поэтому изменения формального
параметра не меняют исходный объект. Временные буферы размещаются в начале
функции и переиспользуются при повторных вызовах в цикле.

Для `long double` используется `x86_fp80`: 80 бит значения в 16 байтах
памяти. Аргументы передаются на стеке, результаты — через x87; они не
расходуют GP/SSE-бюджеты. Агрегаты учитывают классы X87/X87UP и их слияние;
поддерживаются память/`byval`, результат `x86_fp80` либо `sret` в зависимости
от типа. Константы и глобальные инициализаторы сохраняют расширенную точность.
Примеры, ABI, проверки GCC/Clang и границы смешивания с native-бэкендом — в
[руководстве по `long double`](llvm-long-double-ru.md).

Локальные `union` можно инициализировать целым значением, включая результат
вызова функции. Инициализация целым union-выражением для объектов со
статическим временем хранения пока диагностируется.

У закрытых `case`/`enum`/`nullptr`/`union` с `const` индексы специализаций
и размер известны при компиляции. `case get_subtype_index(Type.specialization)`
принимается как обычная константная метка; номера объектов и обработчиков
согласованы в native/LLVM-модулях. Когда закрыты все процедурные типы функции
и локальные объявления покрывают всю матрицу, создаётся неизменяемый массив
адресов и защищённый `switch` с прямыми вызовами. Общий обработчик заполняет
свободные ячейки, конкретные имеют приоритет; предел — 16 ячеек во всей
матрице. Runtime-регистрация и запасной
косвенный путь сохраняют внешние обработчики; подробности — в
[руководстве по диспетчеризации](ppc-closed-dispatch-ru.md). Новый порядок
регистрации требует чистой пересборки PPC-объектов и библиотек. Команды,
правила ABI и примеры — в [руководстве](ppc-closed-indices-ru.md).

Поддержка 4П использует общий с x86-64 AST: скрытые теги, таблицы обработчиков,
runtime-индексы и регистрация из разных единиц трансляции. Приоритеты
конструкторов и деструкторов переносятся в `llvm.global_ctors` и
`llvm.global_dtors`. Проверены `case` и `enum`, общий и нулевой обработчики,
мультиметод, динамическое создание специализаций и полнота закрытого обобщения.
LLVM IR также содержит метаданные закрытых функций для
[межмодульного отчёта](ppc-dispatch-report-ru.md); ссылки на обработчики
сохраняются при `llvm-link`, включая переименование частных функций.
Схема v2 описывает также функции регистрации; отдельный
[режим закрытой программы](ppc-static-dispatch-ru.md) проверяет их перед
заменой таблицы константным массивом и удалением её runtime-поддержки.
Он также [подключён к публичному компилятору и CMake](llvm-closed-compiler-ru.md)
через `--closed-program` с раздельными промежуточными IR-объектами.
Сравнение runtime, защищённого `switch` и обоих статических вариантов доступно
в [бенчмарке закрытой диспетчеризации](llvm-static-dispatch-benchmark-ru.md).

Допускаются вызовы внешних вариадических функций с целочисленными,
указательными и вещественными аргументами, например `printf` и runtime-вызовы
`dprintf`. Для узких целых применяется обычное продвижение к `int`,
для `float` среди аргументов `...` — к `double`.

Поддерживаются также определения вариадических функций C и обработчиков 4П:
`va_start`, `va_arg`, `va_copy`, `va_end`, передача `va_list` в функции libc
и между модулями GCC/Clang. Учитываются именованные параметры, аргументы на
стеке и скрытый результат структуры. Подробности и команды проверки — в
[руководстве по вариадическим функциям](llvm-varargs-ru.md).

Локальные переменные представляются через память (`alloca`, `load`, `store`),
после чего проходы LLVM могут преобразовывать подходящие значения в SSA.
Данные и правила вызовов сохраняют соглашения выбранной платформы.

Локальные VLA, многомерные массивы и прямой `alloca(size)` используют
динамическую инструкцию LLVM `alloca`. Для массивов объектов 4П сохраняется
автоматическая установка признаков. Размеры, выравнивание, время жизни и
ограничения параметров описаны в [руководстве по VLA](llvm-vla-ru.md).

Воспроизводимое сравнение исходного IR, `mem2reg`, `sroa`/`mem2reg` и
`default<O2>` доступно через цель `llvm-opt-demo`. Описание программы,
результаты и команды изучения IR приведены в
[первом исследовании оптимизаций LLVM и 4П](llvm-optimization-ru.md).
Цель `llvm-dispatch-demo` дополнительно использует `llvm-link` для
[сравнения диспетчеризации и видимости модулей](llvm-dispatch-ru.md).
Цель `llvm-pgo-demo` исследует
[оптимизацию вызовов по профилю выполнения](llvm-pgo-ru.md); для неё нужны
также Clang, `llvm-profdata` и runtime профилирования compiler-rt из линии 23.
Цель `llvm-pgo-bench` добавляет [замеры времени native, O2 и PGO](llvm-pgo-benchmark-ru.md)
на тех же обработчиках; для организации повторов нужен Python 3.8 или новее.
Цель `llvm-figures-bench` переносит [исследование на коллекцию фигур и сортировку](llvm-figures-benchmark-ru.md),
используя библиотеку `ppVector`, два профиля обучения и отдельные контрольные данные.

Backend явно диагностирует неподдерживаемые возможности:
агрегаты среди неименованных аргументов `...`, битовые поля,
агрегатные `va_arg` и аргументы без прототипа, TLS, атомарные операции,
объекты и обращения с `volatile`, inline asm
и вычисляемый `goto`. Инструкция LLVM `alloca`, используемая для обычных
локальных переменных, поддерживается. Полная совместимость со всем языком C
и самокомпиляция через LLVM
относятся к следующим этапам. Существующий backend x86-64 сохраняет прежний
набор возможностей.

Обычный `switch` поддерживается вместе с `case`, `default`, fallthrough,
вложенными циклами и GNU-диапазонами `case a ... b`. Условие проходит
целочисленные продвижения, значения меток сохраняют нужную 32-/64-битную
ширину. [Устройство генерации и проверки](llvm-switch-ru.md) описаны отдельно.

## Проверки

GitHub Actions выполняет отдельные native- и LLVM-проверки. Установка
закреплённых инструментов, состав целей и артефакты описаны в
[руководстве CI](llvm-ci-ru.md).

После конфигурации CMake:

```sh
cd build
make test-all         # прежние проверки x86-64, stage2 и примеры 4П
make test-llvm        # LLVM backend компилятора stage1
make test-llvm-stage2 # тот же backend в компиляторе, собранном через stage1
```

`test-llvm-stage2` проверяет работу нового генератора в самокомпилированном
компиляторе. Сам stage2 пока собирается существующим backend x86-64.

CMake по умолчанию предпочитает `llvm-as`, `opt` и `llc` из `PATH`, затем
проверяет имена с суффиксами 23, 22, 21, 20 и 19. Найденные пути печатаются
при конфигурации. Предпочтительный суффикс можно задать
при настройке нового каталога сборки, например:

```sh
cmake -S . -B build-llvm23 -DPPCHIBICC_LLVM_VERSION=23
cmake --build build-llvm23 --target test-llvm test-llvm-stage2 llvm-opt-demo
```

`PPCHIBICC_LLVM_VERSION` выбирает внешние инструменты LLVM. Компилятор,
которым собирается сам ppchibicc и вспомогательные C-модули тестов, задаётся
отдельно через `CMAKE_C_COMPILER`. Для проверки полного цикла с Clang 23
можно создать новый каталог сборки и указать `-DCMAKE_C_COMPILER=clang`,
если команда `clang` в `PATH` соответствует версии 23.

Найденные пути сохраняются в CMake cache. При смене версии в уже настроенном
каталоге одно изменение `PPCHIBICC_LLVM_VERSION` не заменяет сохранённые пути.
Для разделения версий удобно использовать отдельные каталоги; также пути
можно задать явно:

```sh
cmake -S . -B build \
  -DPPCHIBICC_LLVM_AS=/path/to/llvm-as \
  -DPPCHIBICC_LLVM_OPT=/path/to/opt \
  -DPPCHIBICC_LLVM_LLC=/path/to/llc
```

Инструменты LLVM требуются только для этих отдельных целей. `test-all` не
зависит от их наличия. При явном запуске LLVM-проверок отсутствие инструментов
или несовпадение их версий считается ошибкой.

Для каждой небольшой программы тесты проверяют корректность IR, затем
сравнивают вывод и код завершения трёх вариантов: существующего backend,
LLVM без оптимизаций IR и LLVM после `default<O2>`. Отдельная единица
трансляции, собранная системным C-компилятором, проверяет скалярный ABI в обе
стороны; структуры передаются между компиляторами через указатели и по значению.
Для `record-abi`, `floating` и `floating-abi` эталоном служит системный
C-компилятор: у существующего x86-64 генератора есть ограничения для некоторых
граничных случаев ABI, NaN в условиях и преобразований больших беззнаковых
целых. Эти ограничения не переносятся в LLVM backend. Вещественные тесты
проверяют точность констант, преобразования, NaN, бесконечности и знаковый ноль,
вызовы в обе стороны между LLVM и системным C-компилятором, смешанные
целочисленные и SSE параметры, передачу более восьми вещественных аргументов,
обратные вызовы, внешние данные и продвижение `float` в вариадических вызовах.
Проверяются малые и крупные структуры, вложенные поля, указатели, объединения,
упакованные и выровненные типы, нехватка регистров, скрытый указатель результата,
косвенные вызовы и повторные вызовы в цикле. Тесты структур с вещественными
полями охватывают одиночные `float`/`double`, пары и массивы `float`, смешанные
поля в одной и разных восьмибайтовых частях, объединения и границы обоих
классов регистров. Проверяется, что передача структуры через память не
занимает регистры, доступные следующим аргументам. Именованные агрегатные
параметры внешних вариадических функций также поддерживаются; ограничение
касается только агрегатов среди аргументов `...`.

Межмодульный пример 4П проверяется целиком через оба backend, а затем с каждой из четырёх
единиц трансляции по очереди, собранной нативным backend, при остальных
LLVM-объектах. Проверяются также runtime-ошибки отсутствующего обработчика и
неполного закрытого обобщения, включая обработчики с агрегатным и вещественным
результатом и агрегатными вещественными параметрами, диагностика
неподдерживаемых конструкций и режимы командной строки.

Исходный `.ll`, bitcode, преобразованный IR и результаты выполнения
сохраняются в `build/llvm-test` или `build/llvm-test-stage2`. Для воспроизводимого
сравнения оптимизаций следует фиксировать версию LLVM, commit исходников,
параметры целевой платформы и полную последовательность проходов.

Проверки [реальных программ 4П](llvm-real-programs-ru.md) сравнивают native,
обычную и закрытую LLVM-сборку на закреплённых исходниках `4P-examples`.

Для измерения времени на вычислительном многомодульном примере добавлен
[ограниченный запуск «Жизни» на торе](llvm-life-benchmark-ru.md), с независимым
эталоном и сохранением открытых runtime-таблиц.

Общий frontend проверяет [размеры таблиц мультиметодов](ppc-table-dimensions-ru.md)
и использует 64-битные произведения/индексы для обоих backend.
