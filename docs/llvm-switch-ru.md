# Switch в LLVM backend и проверка реальных примеров

LLVM backend ppchibicc поддерживает `switch`, `case`, `default`, переход
к следующей ветви без `break`, вложенные переключатели и циклы. `break`
выходит из ближайшего цикла или переключателя, а `continue` из ветви switch
переходит к продолжению окружающего цикла. Разрешён и обычный `goto` к метке
внутри ветви, как в C.

## Представление в IR

При обычном входе в `switch` условие вычисляется один раз. Для обычных меток
используется инструкция LLVM:

```llvm
switch i32 %value, label %default [
  i32 1, label %case1
  i32 2, label %case2
]
```

При отсутствии `default` общий переход ведёт за пределы переключателя.
Ветки сохраняют исходный порядок выполнения и fallthrough. Даже пустой
переключатель вычисляет выражение условия. Выбор таблицы переходов или другой
машинной реализации выполняют проходы LLVM и `llc`.

Поддерживаются GNU-диапазоны `case a ... b`. Для них генерируется проверка
`unsigned(value - a) <= unsigned(b - a)` в ширине условия, затем выполняется
обычный `switch` для одиночных меток. Вычитания в IR не имеют `nsw`/`nuw`:
переполнение намеренно обрабатывается по модулю. Диапазон размером в миллиарды
значений или весь `unsigned long` не превращается в миллиарды записей IR.

## Типы и общие исправления C

Условие должно быть целочисленным. `_Bool`, `char` и `short` продвигаются
к `int`; на текущей платформе `int` имеет 32 бита, `long` и `long long` — 64.
Значения `case` преобразуются к продвинутому типу условия до проверки
совпадений. Поэтому `case -1` и `case 0xffffffffU` совпадают для 32-битного
условия, но отличаются при знаковом 64-битном условии.

Повторные `case`, пересекающиеся диапазоны, повторный `default` и неверные
типы условия/меток диагностируются общим frontend. Проверка диапазонов
учитывает знаковость продвинутого типа.

Вместе с этим исправлены общие вычисления целочисленных констант. Промежуточные
результаты сохраняют ширину своего типа: `~0U` даёт `UINT_MAX`, а
`0xffffffffU + 1U` даёт ноль и при последующем преобразовании к `long`.
Знаковый результат `(int)0xffffffffU` сохраняет значение −1 при переходе к
64 битам. Исправления действуют также в статических инициализаторах.

Значения меток больше не обрезаются до `int` при разборе. Исходный x86-64
backend использует полные 64-битные константы для сравнения и вычисляет
ширину диапазона без знакового переполнения. Семантика и ABI 4П сохраняются.

## Проверки

Общий файл `test/switch.c` выполняется в native-наборе stage1/stage2 и включён
в LLVM-фикстуру. Эталон также собирается системным C-компилятором. Проверены:

- обычные ветви, несколько меток подряд, `default` в середине и его отсутствие;
- продвижения узких типов, enum, знаковые/беззнаковые 32- и 64-битные границы;
- вложенные switch/циклы, `break`, `continue`, метки внутри `if`, `goto` и Duff's device;
- однократное вычисление условия, в том числе без меток;
- отрицательные, преобразованные и огромные GNU-диапазоны;
- диагностики повторов, пересечений и неверных типов;
- вычисления констант с преобразованием знака и переполнением беззнаковых типов.

```sh
cmake -S . -B build-llvm23 -DPPCHIBICC_LLVM_VERSION=23
cmake --build build-llvm23 --target test-all test-llvm test-llvm-stage2
```

Проверено на LLVM 19.1.7, 21.1.8 и 23.1.6 при O0/O2. Набор включает как
ручную цепочку LLVM, так и `--backend=llvm` с линковкой из ppchibicc.
Самокомпилированный stage2 проверен с LLVM 23.

## Аудит остальных примеров

Скрипт `cmake/audit-llvm-examples.py` находит CMake-проекты с явным `project()`
под `examples/` и пробует каждый целиком через LLVM O2. После ошибки
повторяет сборку исходным x86-64 backend, чтобы отличить ограничение LLVM
от общей проблемы проекта. Входные исходники и CMake-файлы не изменяются.
Временная программа-обёртка задаёт backend последним аргументом, в том числе
для старых проектов с собственными настройками компилятора.

Для проектов фигур с `data/input1.txt`/`output1.txt` и единственной программой
проверяется также результат; сравнение нормализует CRLF/LF. Для остальных
проектов успешная сборка означает только сборку, без проверки выполнения.

```sh
python3 cmake/audit-llvm-examples.py --compiler "$PWD/bin/ppchibicc"
cat build-llvm-example-audit/report.md
```

Нужны Python 3.8+, CMake и согласованные `opt`/`llc`. Скрипт использует `PATH`
и экспортированные `PPCHIBICC_LLVM_OPT`/`PPCHIBICC_LLVM_LLC`. Для нестандартного
CMake доступен `--cmake /path/to/cmake`, для вывода — `--output /path/to/results`.
Каждый запуск создаёт новую директорию сборок; `results.json` содержит статусы,
версии инструментов, хеш компилятора и пути к логам, `report.md` — сводку.
Ожидаемые ошибки совместимости записываются в отчёт и не делают аудит
регрессионным target с требованием успешности всех проектов.

Прогон на LLVM 23.1.6 от 2026-11-11 дал:

| Результат | Проектов | Наблюдение |
| --- | ---: | --- |
| LLVM-сборка прошла | 15 | У 12 также совпал выходной файл фигур; 3 проверены только сборкой |
| LLVM не принял сигнатуры, native собрал | 8 | Первая ошибка: вариадическое определение или объявление/определение с `()` |
| Ошибка CMake-настроек при обоих backend | 15 | 14 проектов животных и `e-life`: для `.ppc` не передаётся `-x c`, а заголовки ошибочно помечены как C-исходники |

Эти числа относятся к полным CMake-проектам. Например, `ppVector` отдельно
собирается через LLVM, но весь проект `vector-list-lib` останавливается
на функциях `pplist`.

Назначение расширений фиксировано: `.ppc` — файлы реализации, а `.pph` —
только заголовки для `#include`. Их не нужно компилировать отдельно.
Указанная группа из 15 ошибок относится к настройкам сборки, а не к поддержке
языковых конструкций LLVM backend. Проверенный вариант CMake приведён в
[инструкции компилятора](llvm-compiler-ru.md#файлы-ppc-и-pph).

Ближайшие задачи по результатам аудита:

1. Согласовать оставшиеся действительно безаргументные сигнатуры `()` с `(void)`
   во всех объявлениях и обработчиках. Полноценные вариадические определения
   требуют отдельной реализации.
2. Уточнить CMake-настройки для нестандартных расширений: `LANGUAGE C` при
   compiler ID `unknown` не обеспечивает передачу `-x c`. Такой параметр нужен
   на стадии компиляции `.ppc`; переносить его в общие флаги линковки не следует.
   Заголовки `.pph` и `.h` должны подключаться через `#include` и могут оставаться
   в списке target с `HEADER_FILE_ONLY TRUE`. `LANGUAGE C` применяется только
   к файлам реализации.

После устранения первых ошибок аудит нужно повторить: текущий результат
не утверждает, что за ними нет других ограничений.
