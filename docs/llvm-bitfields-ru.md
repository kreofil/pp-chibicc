# Битовые поля в LLVM

LLVM-бэкенд поддерживает целочисленные битовые поля в структурах и
объединениях на Linux x86-64. Разметка общая с native-бэкендом: учитываются
ширина и знак поля, `__attribute__((packed))`, безымянные поля и разделители
нулевой ширины. Поля доступны также внутри обобщений и специализаций 4П.

```c
struct Flags {
  unsigned level:3;
  int adjustment:5;
  bool enabled:1;
};

struct Flags flags = {7, -3, true};
flags.level++;                 // 7 -> 0
int value = (flags.level = 10); // поле и результат присваивания равны 2
```

## Чтение, запись и выражения

Чтение извлекает биты поля и выполняет знаковое или нулевое расширение.
Запись сохраняет соседние биты. Присваивание, составное присваивание и
префиксные операции возвращают усечённое значение; постфиксные операции
возвращают прежнее значение. Выражение, вычисляющее адрес структуры,
выполняется один раз.

Для `_Bool`/`bool` допустима ширина 1; значение нормализуется в 0 или 1
до записи. Поддерживаются также другие целочисленные базовые типы размером
до 64 бит, включая расширение с `long`. Ширина — целочисленное константное
выражение от 0 до ширины типа. Поле нулевой ширины должно быть безымянным.
Атомарные битовые поля и `_Alignas` на битовом поле диагностируются.

Целочисленные продвижения учитывают диапазон поля. Например, `unsigned :3`
продвигается до `int`, а `unsigned long :32` — до `unsigned int`. Это относится
к арифметике, сдвигам, `switch` и передаче скалярного значения среди `...`.
Для расширенных полей шире 32 бит сохраняется базовый тип, как в Clang;
GCC использует собственные расширенные типы, поэтому результаты `_Generic`
для таких полей могут отличаться.

Адрес отдельного битового поля получить нельзя. Прямое применение `sizeof`,
`_Alignof` или `typeof` к полю также диагностируется; `sizeof(+flags.level)`
допустим и относится к продвинутому целочисленному типу.
`typeof` составного выражения, например `typeof((0, flags.level))`, задаёт
полный базовый тип, как в Clang: новая переменная не наследует ограничение
диапазона битового поля. GCC может раскрывать собственный узкий расширенный тип.

## Размещение и ABI

Обычные битовые поля не пересекают границу единицы хранения базового типа.
В `packed`-структуре такое пересечение допускается. Поле шириной 64 бита
может занимать части девяти байтов. Чтение и запись затрагивают только
занятые полем байты; доступ к хвосту маленького объекта не читает за его
границей. В LLVM используются целые нужной ширины, вплоть до `i72`, и
операции маскирования. Оптимизатор может упростить их дальше.

Безымянные поля не занимают позиции в списке инициализации и сами по себе
не повышают выравнивание структуры. Поле `:0` выравнивает следующую позицию
до границы базового типа. Поддерживаются локальная и статическая
инициализация, включая поля после безымянных разделителей и поля объединений.

Структуры и объединения передаются по значению через INTEGER/SSE-регистры
или память согласно используемой классификации System V. Именованные
битовые поля дают класс INTEGER только для занятых байтов; безымянные поля
считаются заполнением. Проверены взаимные вызовы с GCC и Clang, обратные
вызовы через указатель, смешанные вещественные поля, нехватка регистров и
большие результаты через `sret`.

У GCC и Clang существуют расхождения ABI на редких комбинациях битовых
полей. В частности, для `packed`-структуры с невыровненным вложенным
агрегатом, состоящим исключительно из битовых полей, LLVM-бэкенд следует
Clang и использует память; GCC может использовать регистры. Для агрегата,
состоящего только из безымянных битовых полей, LLVM/Clang не расходуют
регистры аргументов, а GCC может расходовать целочисленный регистр. Такие
типы между GCC и LLVM следует передавать через указатель. Объединение, в котором
битовое поле меняет только верхнюю восьмибайтовую часть класса X87,
диагностируется при передаче по значению: GCC и Clang также расходятся
в его ABI. Хранение и доступ к такому объединению через указатель допустимы.

Поддержка битовых полей не снимает ограничений на `volatile`, TLS, атомарные
операции. Агрегаты среди неименованных вариадических аргументов поддерживаются;
см. [правила передачи и чтения](llvm-vararg-records-ru.md). У native
сохраняются прежние ограничения ABI сложных упакованных и X87-агрегатов.

## Пример 4П и проверки

```sh
cmake -S . -B build
cmake --build build -j
bin/ppchibicc --backend=llvm -O2 examples/llvm/ppc-bitfields.c -o build/ppc-bitfields
build/ppc-bitfields
cmake --build build --target test-all test-llvm test-llvm-stage2
cmake --build build --target test-llvm-closed-compiler test-llvm-closed-compiler-stage2
```

Пример выводит:

```text
normal=3 extra=16
normal=4 extra=0
```

Проверки включают значения на границах диапазонов, сравнение с GCC/Clang,
упакованные поля с пересечением байтов, доступ рядом с защищённой страницей,
диагностику недопустимых объявлений, режимы `runtime`, `table`, `switch`
и закрытую сборку. Старый тест `test/bitfield.c` также выполняется через LLVM.

Изменения общей разметки исправляют прежние случаи с упакованными и
безымянными полями. После обновления нужно пересобрать все объектные файлы,
взаимодействующие через такие структуры. Метки 4П и протокол регистрации
обработчиков не меняются.
